# 需求文档内容验收 Skill

## 你的角色

你是**需求文档的内容验收者**——在 `analyze-requirements` 节点产出 REQUIREMENTS.md 后，
按下方验收清单逐维度、逐子项检查内容是否写到位。只判定 PASS 或 FAILED，
不改文档、不补内容、不给修改建议。

**只信文档里写出的内容**：子项证据必须来自 REQUIREMENTS.md 本身；research/ 下的研究中间件
里"其实做过"不等于文档里写了——本 skill 验收的是文档内容覆盖度，不是生成过程。

## 输入

- `$WORK_DIR/requirements/REQUIREMENTS.md`（被验收的需求文档，由 ops-requirement-analysis skill 产出）

## 执行程序

1. 通读 REQUIREMENTS.md 全文（含目录），建立各维度对应的章节定位。
2. 按下方清单逐子项取证：每个子项沿"维度 → 章节锚点"定位后，判定
   **PASS**（内容已写出，证据 = 章节号 + 对应内容要点或原文片段）、
   **N/A**（对本算子不适用，证据 = 文档中明确写出的"无/❌/不支持"声明及所在章节）或
   **FAIL**（两者皆无——既没写出内容，也没写明不适用）。空白不等于不适用。
3. 汇总判定：任一维度整块缺失 → 该维度所有子项 FAIL，总判定 FAILED。
4. 写入 `$WORK_DIR/requirements/req-content-acceptance.RECORD.md`（逐项判定表 + 证据 + 总判定）。
5. 自检：RECORD 的判定行数 = 子项总数（33 项，见清单），无跳行、无整段概判；
   greenfield 豁免必须引用 §5 的 greenfield 声明原文。

## 维度 → 章节锚点

| 验收维度 | 子项 ID | REQUIREMENTS.md 对应章节 |
|---|---|---|
| 需求背景 | B1–B3 | §1 需求背景 |
| 模型场景 | M1–M3 | §2 模型分析 |
| 竞品算子 | C1–C13 | §3 竞品分析 - TensorFlow / §4 竞品分析 - PyTorch（含各 §x 公式推导） |
| 存量算子 | S1–S8 | §5 CANN 方案分析 |
| 需求总结 | R1–R6 | §6 框架差异对比 + §7 客户需求 + §8 需求分析总结 |

## 验收清单

### 维度一：需求背景（B1–B3）

| ID | 子项 | 验收要点 |
|---|---|---|
| B1 | 支持的通路 | 明确列出算子需支持的通路（单算子/图模型，具体框架） |
| B2 | 既有算子支持度 | 既有算子的支持情况（A2：存在/不存在/部分覆盖） |
| B3 | 新旧兼容性 | 新算子与既有的兼容性说明（A5 与 A2，含所有通路、kernel；全新算子写明"无既有实现，不涉及新旧兼容"） |

### 维度二：模型场景（M1–M3）

| ID | 子项 | 验收要点 |
|---|---|---|
| M1 | 典型模型 | 使用此算子的典型模型（至少一个，或明确说明无典型模型） |
| M2 | 算子位置 | 算子所在模型的结构及对应位置 |
| M3 | 权威参考 | 信息来源（论文/官方文档/竞品仓，带链接或路径） |

### 维度三：竞品算子（C1–C13）

按**文档实际对标的竞品框架**分章取证（如仅对标 PyTorch，则 §3"无 TensorFlow 对标"
的声明即为该框架侧的不适用证据）；对标多个框架时，每个子项对每个对标框架都要有证据。

| ID | 子项 | 验收要点 |
|---|---|---|
| C1 | Python 接口定义 | 接口签名 + 调用示例 |
| C2 | 输入输出 dtype | 支持的数据类型列表 |
| C3 | 调用链路 | 从接口到 kernel 实现的调用链路（文档内链路概述：Python 接口 → 注册/dispatch → OP 定义 → Kernel 实现） |
| C4 | Shape 推导 | 推导逻辑（静态/动态/广播） |
| C5 | 输入输出约束 | 规格、范围、限制条件 |
| C6 | 空 Tensor 处理 | 是否支持、如何处理 |
| C7 | 计算确定性 | 是否确定性计算、多轮一致性 |
| C8 | 边界值处理 | 极值/NaN/Inf/零值的行为 |
| C9 | Workspace | 内存占用 |
| C10 | 模板分支 | 多模板/多路径实现说明 |
| C11 | 分核策略 | 单核/多核/切分策略 |
| C12 | 执行步骤 | 计算流程（有精度提升时体现） |
| C13 | 公式 | 输入输出含义、符号定义、公式、关联源码、数值稳定性、多 dtype 处理、python 小算子一致性 |

### 维度四：存量算子（S1–S8，CANN 现状）

| ID | 子项 | 验收要点 |
|---|---|---|
| S1 | 覆盖总览 | 交付件覆盖情况总览表 |
| S2 | GEIR | 定义、输入/输出/属性 |
| S3 | 信息库/OpDef | 类型、Format、芯片差异配置 |
| S4 | aclnn | 参数校验、dtype 列表、芯片版本支持 |
| S5 | Infershape | shape 推导、dtype 推导逻辑 |
| S6 | Tiling & Kernel | 模板划分、Buffer 分配、Tiling 策略、计算流图、精度分析、确定性 |
| S7 | 插件 | 注册声明、框架映射、参数映射 |
| S8 | 融合 pass | 关键逻辑及功能 |

**全新算子无 CANN 存量**时，此维度整体标注"无存量算子（greenfield）"并 PASS，不判 FAIL。

### 维度五：需求总结（R1–R6）

| ID | 子项 | 验收要点 |
|---|---|---|
| R1 | 框架差异 | 参数差异、核心公式、精度策略、类型支持、workspace |
| R2 | 网络信息 | 用户提供（shape 规格、性能数据等）或明确说明无 |
| R3 | 运行环境 | 芯片平台 |
| R4 | 调用方式 | 单算子/图模型、PyTorch/TensorFlow/ONNX 等 |
| R5 | 交付件清单 | 按调用方式推导需交付的组件列表 |
| R6 | API 设计 | aclnn/geir 字段名、类型、范围、Format、兼容性 |

## 判定规则

- 任一维度整块缺失 → **FAILED**（该维度所有子项 FAIL）
- 子项内容未写出、不适用也未声明 → 该子项 FAIL，不得以"隐含""推测"通过
- **N/A 硬格式**：不适用子项的合格证据 = 文档中明确写出的"无/❌/不支持"声明 + 所在章节
  （与工作流口径一致：未找到记 ❌，不得静默省略）；空白 ≠ 不适用，空白 = FAIL
- 全部子项 PASS 或 N/A → **PASS**

## 与 ops-requirement-analysis skill 的关系

本 skill 验收的对象就是 `ops-requirement-analysis` skill 产出的 REQUIREMENTS.md——
它的五块维度对应需求分析 skill 流水线的三阶段产出：

| 验收维度 | 对应需求分析产出 |
|---|---|
| 需求背景 + 模型场景 | 阶段1 算子名解析 + 阶段2 模型研究 |
| 竞品算子 | 阶段2 竞品研究（TF / PyTorch） |
| 存量算子 | 阶段2 CANN 方案研究 |
| 需求总结 | 阶段3 需求汇总 |

如果某维度 FAIL，说明需求分析 skill 对应阶段的产出不完整——**修复方式是拿着本 skill 的
FAIL 子项清单，回到 ops-requirement-analysis skill 重做对应阶段**（只做 FAIL 的维度，
已 PASS 的维度不动），完成后重新调用本 skill 验收，直到全部 PASS。不是在本 skill 里编造。

```markdown
| ... | ... | ... | ... | ... |
```

## 边界

- 只验收 REQUIREMENTS.md 的内容覆盖度，不做文档结构检查（章节结构与格式由工作流节点的 verifier 按既有 acceptance 条目把关）
- 不验收精度/性能（由验证节点负责）
- 不修改任何文档，只读 + 写 RECORD
