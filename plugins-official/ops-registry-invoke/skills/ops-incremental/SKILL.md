## 流程

1. **需求分析。** 保留用户原始需求、验收条件与授权；定位目标算子和工程位置。
   确认这是已有算子的有界增量：不改变公开接口与既有数值语义，改动不超出
   目标算子包。验收基线：改前状态目标能力缺失（验收失败），完成后通过；
   全量回归与性能不劣化是硬门。缺失信息只澄清必要的部分。
2. **选择工作流模块。** 通读 ops-registry-invoke skill 的 `workflows/` 下已有
   工作流模块（如 op-design、op-impl、op-update、code-review、doc-gen、
   requirements-spec、env-setup），按本次需求挑选可复用的任务。能复用的必须
   复用；只有真实缺口才新建通用任务，并写明为何无法复用。
3. **生成 workflow.yaml。** 把通用任务与所选模块任务实例化并连成有向无环图：
   每个任务写清目标、验收、依赖与重试，测试先行。yaml 写入本次独立运行目录，
   是本次专属产物；任务结束后归档，下一项需求重新生成。
4. **交给 workflow-orchestrator。** 在本次运行目录用 workflow-orchestrator 执行
   生成的 yaml：编排器的任务状态与证据（`.workflow/`、日志）必须落在该目录。
   原样交接用户 prompt、work_dir 与 provider，跟踪运行至完成，交付结果与
   未完成项。不得绕过编排器自行执行任务，也不得只在临时目录演练 yaml 后
   代替执行。plan-only 时生成并检查 yaml 后停止，并明确说明未执行。

## 通用任务

一次增量工作流通常由以下通用任务构成；生成 yaml 时按本次需求实例化、裁剪
或补充，能对应到工作流模块的优先复用模块任务。分析类任务以**核对为目标**
而非穷举：范围限于本次增量触及的交付件与直接依赖，逐项核对即止，不做全包
或全库扫描，不复述与本次增量无关的实现；需要什么查什么，查到即收。

- **现状分析**：针对目标能力核对其缺失与可复用项，产出可核对的现状结论
  与复用依据；禁止扩展为全量盘点。
- **基线构建**：在改前状态完成构建并运行既有测试，记录基线结果，作为
  delta 测试预期 RED 和后续全量回归的对照。
- **涉及交付件分析**：确定本次变更影响的交付件（实现、测试、文档、构建
  配置等）与有界改动范围，明确不改动项及其理由。
- **增量需求实现设计**：给出满足需求的最小改动设计、各任务验收标准与
  依赖顺序，声明对既有行为的预期变化与不变量。
- **delta 测试（改前 RED）**：在改动前添加聚焦的增量测试，并确认其按
  预期失败；基线缺失不能由设施错误制造。
- **实现**：最小改动使 delta 测试与相关既有测试 GREEN，不引入无关变更。
- **全量回归**：运行全量测试与性能对照，回归不通过或性能劣化即失败。
- **评审与修复**：对改动做独立评审，发现问题回到对应任务修复后重跑验收。
- **文档校验**：核对受影响文档与实际行为一致，文档与代码不一致不得通过。
- **交付**：按既有授权提交、推送并创建 PR，改动不得超出已分析的交付件范围。

## 边界

- 不修改用户已有改动；规划期间源码只读。
- 独立验证失败或运行中断时保存现场、报告并结束本次调用，不自动恢复或另起运行。
- 结构校验和 dry-run 不等于功能验证通过；提交、推送和 PR/Issue 按既有用户授权处理。
