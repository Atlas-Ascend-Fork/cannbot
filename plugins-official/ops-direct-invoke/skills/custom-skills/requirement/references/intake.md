# 需求对齐与交接

在当前用户会话中完成，不作为 harness 节点执行。交付 `work_dir/需求分析.md`；work_dir 沿用调用方分配的 `.cannbot/<任务名>/workflow<序号>/`。内容按 [需求 checklist](requirement-checklist.md) 填写，任务是明确用户意图与开发边界，不替开发阶段完成技术方案或设备验证。

沿用 init 已确定的仓库、平台、开发语言及交互偏好；已有明确授权的选择范围不重复确认。项目配置中的 `language` 为 `ascendc` 或 `dsl` 时沿用；缺失或为 `unspecified` 时在当前任务中按下文规则确定。当前任务明确指定的语言优先，并核对平台支持范围。

## 交互偏好

读取项目 `.cannbot/ops-direct-invoke.json` 的 `preferences.interaction` 和自动生成的 `autonomy`；本次用户明确要求优先。下文的问卷与确认按此偏好执行：

| 偏好 | 行为 |
|---|---|
| `autonomous`：静默运行 | 在当前任务和已有修改权限内自主决策，不主动发问或请求确认；记录选择依据。必要输入无法确定时如实交付阻塞，不编造事实。 |
| `confirm`：仅重要节点确认 | 仅确认需求分析中的必要缺项，以及需求、交付标准或权限的实质变化；常规实现、验证和内部启动参数自主处理。 |
| `supervised`：监督所有细节 | 对所有不确定项及时发问卷，等待答复后再执行依赖这些决定的工作；已明确的约定不重复询问。 |

交互偏好不扩大修改权限，不降低验收标准，也不自动批准已有人工门禁。自主选择记录为授权范围内的决策，不写成用户已确认。将本轮偏好和自主范围记入需求交接，后续遇到取舍时继续沿用。

## 首轮集中整理，再分批问齐

需要用户参与时，先向用户提示：“请先不要离开，我会先整理需求和可选环境，集中和你对齐必要的问题。”做轻量只读摸底后，再按交互偏好决定是否形成问卷；不做完整开发、依赖下载或长时间 API 调查。

1. 从用户原话、已有答复和附件提取目标与限制；快速定位已有本地同名任务的 proto、golden 和接口说明，比较数学语义、布局、shape/dtype、attrs 及默认值，再提出候选规格。将影响交付的差异合并进首轮问卷，不先假定布局再返确认。只做可直接定位的读取；未找到或资料尚未下载时记录未知，及时提问，不先遍历源码、下载依赖或完成环境/API 调查。
2. 按 checklist 预填参数，给每项标明值、来源和状态。明确事实直接沿用；能由规格或仓库契约唯一推导的值填入并注明推导依据，不重复询问。名称相同但语义或范围可能不同的资料不能自动视为匹配。
3. 发问前一次汇总已知待决项：开发语言、语义/范围、目标设备与交付标准，以及 conda/Python、CANN 和修改权限。环境候选使用已有记录或调用方的轻量只读探测结果，不把当前 shell 的默认值当成用户选择。优先同批问齐；每批最多五题，工具限制更低时遵守工具限制。超限则连续分批；仅在问题确实依赖前一答复时分阶段，说明依赖并只补问受影响项，避免启动后才发现漏问环境或安装权限。
4. 每题一句话说明待决事项，给出清晰且可区分的预设选项；能给出合理建议时推荐一项并简述依据，允许自由补充。不把整张 checklist 当问卷，不问用户已说明或仓库已有确定答案的字段。

没有关键缺项时，不为凑问卷发问，直接进入清单核对。用户未提出且不会影响交付的用途背景、截止时间、偏好等记“未指定”，不为了填表逐一追问。

## DSL 产物位置

prompt 或问卷已指定 DSL 交付位置时沿用；未指定则默认任务开始的当前执行目录，不为默认值重复提问。相对路径按该执行目录解析，将交付绝对路径及来源写入现有需求清单，后续进入 work_dir 不改变该值。

## 推导边界

- 开发语言先于语言相关推导确定：取用户指定；平台仅支持一种语言时沿用该语言，多种语言可选且未指定或授权选择范围时必须提问，在平台支持的语言中选择；语言问题可与环境、权限及其它独立问题同批提出，不因此单独开一批。确认前不按某一种语言展开工程推导。CANN Bench 的 Ascend C 提交是 `<<<>>>`、`cann_bench` Python 包与同名注册命名空间；选用 CANNBot-DSL 时以其来源仓的源码与构建契约为工程依据，本插件只承接其契约，不复制或覆盖其规则。已有目标 proto 的 schema、golden 和用例范围作为工程依据，保留具体来源与版本。不默认把所有 dtype/shape 都扩展到任意值。
- 执行环境必须有用户选择或明确授权的选择范围：记录已有 conda 环境的名称及绝对前缀、Python 可执行文件，或新环境的位置与创建约束；不使用 conda 时也记录用户选择的解释器。记录 CANN 安装根路径、版本和激活脚本；只有一个候选也不能把探测结果写成用户已选。已有明确指定直接复用，不重复问。
- 修改权限与环境选择一起确认：允许新建环境、补装或升级哪些依赖、能否改既有环境，以及代码与交付目录的写入范围。未授权的系统 Python、CANN、驱动和其它环境不得修改；已有任务授权覆盖的安装与修复不逐条重问。不能用“为了完成任务”推导用户未授权的环境切换。
- 精度承接当前目标仓的 checker 及算子配置，记录取值和出处；用户没有额外精度要求时不要求用户重新选择每个阈值。标准冲突或用户提出另一指标时，说明区别并确认，不自行降低评测门槛。
- 芯片优先使用用户明确目标；没有指定时，可用已核对缓存中唯一可用目标作有依据的建议。目标与缓存不一致或存在多个可选目标时提问，不能将缓存事实写成用户已经选择。
- 技术路线只记录用户的硬约束和授权范围。未指定 SIMD/SIMT、Cube、框架或融合方式时记“未限定，在目标平台上按验证结果选择”，不强制用户预先拍板所有内部实现细节。不把技术可行性待验证误作需求缺失；技术验证的组织方式交给调用方规划。
- 本地功能交付与实际跑分是不同结果。沿用用户的性能目标；仅要求开发算子且无额外性能门槛时，记录可评测源码及功能验证范围，不自行添加 HAP 阈值。用户明确要求实际分数或性能达标时，将其作为交付要求交调用方安排，不能因为现有模板没有性能节点就悄悄删去。

## 答复、确认与交接

问卷发出后保持待答，可并行核对不依赖答案的资料，但不启动依赖未决项的开发。真实答复回填对应条目；未答、预选项、超时或问卷消失都不算确认。问题工具不可继续使用时保留待答清单并在当前会话接续。

向用户简短展示已提取的目标、关键范围及未决决定，让用户容易纠正。已有明确指令、答复或自主授权足以覆盖当前需求时，记录依据，直接沿用，不再追加逐字段问卷或一次重复的总批准。存在影响实现或交付标准的推断/新取舍时，按交互偏好处理，不能把“推断”写成“用户已确认”。

完成条件：必需规格、环境组合和修改权限有具体值或明确授权范围，推导可追溯，关键冲突已解决，内部技术选择留给后续验证。交接绝对路径、版本、目标仓、算子及确认依据；环境选择与环境检查通过是两回事，已知依赖或访问缺口须有授权内的处理安排，不能只凭通用设备检查宣布 DSL 已就绪。

全部需求、环境和权限已确认后，将清单交给调用方；是否还需启动输入确认由调用方按调度契约处理，全部必要确认完成后再通知用户可以离开。已有信息充分时无需需求问卷。后续节点重试、恢复或新建修复 workflow 沿用同一任务约定，不因内部路径、模板文件或 prompt 整理变化重问需求与权限；只有实质变更才合并询问受影响项。未答问题不得视为授权。

本 Skill 不编排 workflow、不调用其他 Skill、不修改 harness 状态。后续发现需求变更时，在当前用户会话中仅核对受影响条目并更新版本；旧确认不能批准新增限制或放宽标准。
