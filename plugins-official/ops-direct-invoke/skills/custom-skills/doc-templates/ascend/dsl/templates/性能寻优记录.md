# 性能寻优记录

寻优节点共用一套台账，避免每轮各写一份报告。文件位置固定为 `$WORK_DIR/opt/`：

| 文件 | 写入节点 | 内容 |
|---|---|---|
| `baseline.yaml` | 寻优基线 | 契约摘要、基线身份、诊断/比较记录路径、预算与授权 |
| `control.yaml` | 寻优基线 | independent 方式的控制样本与原始证据 |
| `controls/<candidate>/<collection>.yaml` | 联合迭代 | interleaved 方式与该候选同次采集的控制记录 |
| `diagnostics/` | 优化阶段按需写入 | 针对具体疑点的原始诊断资料，可不产生 |
| `iteration.yaml` | 联合迭代 | 跨轮计划、反馈、累计预算、当前最佳和恢复依据 |
| `candidates.yaml` | 联合迭代 | 累计候选、派生关系与不可变测前依据 |
| `ledger.yaml` | 联合迭代 | 逐候选的实现、正确性、实测与结论 |
| `measurements/<candidate>/<collection>.yaml` | 联合迭代 | 单候选各次采集记录；原始样本与命令按路径索引 |
| `pre-review.json` | 联合迭代 | 选中实现的来源、源码/测试哈希、运行入口与三组全量精度证据 |
| `pre-review-results/` | 联合迭代 | 选中待检视版本的三组原始全量结果 |
| `decision.yaml` | 联合迭代 | 采用项、收益与淘汰结论 |
| `regression/` | 寻优回归 | 赢家的全量精度与复测原始结果 |
| `selected.json` | 寻优回归 | 最终交付版本指针 |

方法与证据分类参考只读的 `ops-opmodel-toolkit` Skill；本工作流的落盘结构、预算和恢复契约由本文及 task 定义。不要在台账里重复抄录原始日志或逐例明细，只记路径与关键数值。

## 基线

```yaml
contract:
  target: <来自 perf-contract>
  protocol: <共同计时条件及分别冻结的 diagnostics/comparison>
  adopt_rule: <采用条件>
baseline:
  commit: <精度通过实现的 opt/git 原始控制 commit>
  entry: <运行入口>
  cases: [<case_id>]
  total_us: <主算子耗时>
  comparison_record: <independent 为 opt/control.yaml；interleaved 暂为空并明确待同次配对>
budget:
  max_candidates: <N>
  max_rounds: <N>
  stop: <停止条件>
  accounting: <已确认的基线、探索、最终回归开销划分与必要预留>
framework_change_allowed: <原授权记录；本流程不修改 ops-opmodel-toolkit 参考 Skill 及通用框架；算子模型改动沿用已有授权>
```

## 迭代与恢复

`iteration.yaml` 是业务实验索引，不是 harness 状态机。可用现有 YAML 结构表达以下内容，不另造一套模型搜索台账：

| 内容 | 需要保存的事实 |
|---|---|
| 冻结身份 | 原始控制 commit、契约版本及 comparison protocol_id；不随当前最佳更新 |
| 本轮计划 | 稳定轮次 ID、待区分假设、有限实验集合、关联候选及计划消耗；行动前登记 |
| 实际进展 | 各实验未开始/已开始/完成/中断的事实、源码及采集身份、原始证据索引；启动前留下可恢复记录 |
| 累计预算 | 全部已登记完整候选、已开始轮次、实际设备及模型开销、剩余量和最终回归预留；预算口径来自契约 |
| 反馈 | 观察、竞争解释、分类、有效/失败分支、下一步理由及重新打开条件 |
| 当前最佳 | 按冻结目标比较所得的 candidate/commit 和正式证据；没有合格新方案时为原控制 |
| 结束 | 目标是否达成、候选是否可采用、停止原因及未完成范围，分别记录 |

`max_candidates` 是整个优化过程累计登记的完整候选上限，编译/精度失败及未测候选也计入；恢复同一候选不重复占名额，改变结构或参数登记新身份。`max_rounds` 是探索轮次上限，一轮可以只有一个实验，也可以是事先登记的有限集合。读取本轮结果后产生新方向，另开一轮；最小实验、模型修正与反馈不能藏在无限扩展的一轮内。基线采集与最终回归不冒充探索轮次，其开销按契约单独划分和预留。模型 `case_attempts` 只计模型评分，不代表设备预算。

恢复先读取已有进展、验证源码及证据身份，再继续尚未完成的工作。已开始轮次、失败和中断开销不清零；开销无法确认则记未知并在已确认上限内保守处理，不能当作零。保存文件中断造成无法判断是否已执行时，先利用命令和原始文件恢复事实，不重新采集以替代失踪记录。预算或身份无法可靠恢复时停止并报告，不重开一份台账绕过上限。

当前最佳可以成为父候选，允许组合多个已登记来源；原始控制始终保留。旧候选、测前预测和原始样本不可覆写，只有状态及后续判断可以追加修订依据。直接设备实验不强制创建模型搜索会话；用到搜索会话时索引其身份和评价，不复制其模型预算到设备预算。旧路径下已有效的测量可以按身份引用，目录层级变化不要求重测；新的逻辑采集序列使用独立 collection，同一序列的中断恢复见下文，保留所有历史序列。

## 候选

| 字段 | 说明 |
|---|---|
| `id` | 稳定 candidate ID；结构变化产生新版本 |
| `parent` | 父候选、基线或组合来源；对应起点 commit 可恢复 |
| `source` | 语义推导 / 源码审查 / 模型搜索 / 设备反馈 / 用户建议 |
| `change` | 变更点：分块、阶段、缓冲深度、分核、布局或同步 |
| `mechanism` | 预期缩短的关键路径与收益机制 |
| `cost` | 新增的搬运、指令、同步或容量代价 |
| `falsify` | 什么观测会否定该收益机制 |
| `cases` | 适用 case |
| `prediction` | 模型预测值与模型版本；无预测写明“未预测” |
| `search` | 搜索空间、有效参数、评分版本与排名；未使用写明“未使用搜索” |

## 台账状态

`ledger.yaml` 每项至少包含以下状态之一，且允许并列记录不同维度：

| 状态 | 含义 |
|---|---|
| `proposed` | 已登记，尚未实现 |
| `compile_failed` | 编译失败，保留错误证据 |
| `accuracy_failed` | 原正确性标准未通过 |
| `not_measured` | 实现完成但无有效测量 |
| `measured_slower` | 同口径有证据支持相对控制变慢；未分辨出改善不自动记变慢 |
| `measured_best` | 按冻结目标在已测可比集合中最佳；是否满足采用条件单独记录 |
| `cost_unknown` | 模型关键成本未验证，不参与有效模型排名；独立设备实测资格另行判断 |
| `evidence_insufficient` | 样本不齐、不可比或收益未超出可分辨波动，保留证据但不作为采用依据 |
| `rejected` | 已淘汰，记录层次与重新打开条件 |

## 结论

`decision.yaml` 至少包含：

- `adopted`: candidate ID 或 `baseline`（保留原控制）
- `commit`: 采用版本
- `gain`: 相对基线的完整耗时变化与统计口径
- `response`: 采用的收益机制与代价
- `unexplained`: 尚未解释的偏差
- `rejected`: 淘汰候选的层次、最小反例与重新打开条件
- `target_response`: 原始要求与自然语言目标的逐项结果、方法及证据
- `termination`: 停止原因、目标达成情况、已用/剩余预算与未完成范围

统一检视消费 pre-review 后产生 review-fix/selected.json；最终验证对整改后版本生效，通过时才生成 opt/selected.json。检视阶段的 baseline_fallback 是待检视版本，可能是候选，并非原始性能控制。最终验证否定采用时保留 decision 与失败证据，终止并撤销失效交付指针；原始控制未检视时不得直接交付托底。

## 约束

- 采用只依据同口径实测；模型评分、搜索排名与代理分数不得写入 `gain`。
- 未实测候选不得进入 `adopted`。
- 正确性未通过的候选不参与性能排名，其测量只作为诊断证据。
- 未达到 `target` 时如实记录未达成项，不把预算耗尽表述为达标。

## 测量证据

每份诊断/比较测量分别记录，不混用样本。对 `comparison`，基线、候选和最终复测使用同一 snapshot；版本不同单独记录 commit，不通过修改协议隐藏差异。示例结构：

```yaml
protocol: <check_perf_contract.py 输出的 snapshot 原样结构>
protocol_id: <同次输出的 protocol_id>
commit: <本次实际加载的源码版本>
entry: <本次实际调用入口>
case_version: <CSV、配方、seed 和相关输入资产的共同版本或组合哈希>
collection_id: <本次采集序列的唯一 ID；交错方式的基线和候选必须相同>
cases:
  - id: <契约 case ID>
    samples:
      - id: <唯一采集尝试 ID>
        status: valid
        duration_us: <实际设备耗时>
        pair_id: <交错比较时必填，同一对的基线和候选相同>
        concurrency: <observed / not_observed / unknown>
        raw_path: <原始采集文件路径，附任务与调用位置关联>
      - id: <另一无效尝试 ID，仅适用时记录>
        status: invalid
        failure_kind: <tool_error / missing_data / unmatched_task>
        reason: <错误依据>
        concurrency: unknown
        raw_path: <失败日志路径>
```

`samples` 保留全部尝试，先按配置完成固定数量的有效样本，再按预定统计量汇总。并发观测不是丢弃依据；慢样本不能伪装为工具失败。重复中途失败的已完成有效样本不因重试被覆盖。交错采样的一端无效时保留记录，后续有效配对须在同一 collection_id 内、双方使用相同 pair_id，不能拿不同时段的样本冒充配对。

执行者运行 `"$PYTHON" "$WORK_DIR/scripts/check_perf_contract.py" --contract <契约> --purpose comparison --measurement <本次记录> --reference <基线记录>`，检查协议身份、case 集及版本、有效样本数量、无效重采预算和 pair_id 对齐。诊断记录用 `--purpose diagnostics --measurement <记录>`。各阶段报告保存命令、输出与退出码；verifier 审查已有记录，不重复上板。

脚本是结构与完整性检查，不验证原始日志真实性、不自动判断稳定改善，也不能发现未登记的采集。执行者与 verifier 仍须对照原始文件、实际命令和全部尝试，确认计时边界、预热、采样顺序、统计量及版本真实一致；解释分布与测量限制，不能把结构检查通过写成性能达标。

### 中断后继续同一逻辑采集

collection_id 标识事先计划的逻辑比较序列，不等于某次采集进程。中断恢复先核对实际源码、协议、输入、环境及比较资格；仍有效时使用同一 collection，保留全部既有有效及无效尝试，仅补不足部分，必要预热按原协议执行并另记恢复时间。每个 case 最终仍恰好达到冻结有效样本数，无效补采在同一逻辑序列累计，不能恢复时重新领取额度。

interleaved 只有双方均在中断前实际完成的整对才作为有效比较样本保留。中断的半对不与恢复后另一端拼接：保留该侧原始结果和原状态，比较记录将其注明为 `status: invalid`、`failure_kind: missing_data`，reason 说明配对另一端缺失，引用原始文件；这不是丢弃慢样本，并计入无效补采上限。补采时双方实际运行一个新的 pair_id。无效额度不足时停止并标证据不足，不隐去半对。

版本、输入或实际计时条件变化使旧证据失去资格时，才按既定预算另建 collection，保留旧片段、变化原因及累计开销；不把跨序列样本合成一份通过检查的记录，也不从多次完整序列中挑最快者。仍可比的完成整对不因重启而失效，共享观测本身不作为另开序列或废弃样本的理由。预算明确限制的总开销始终跨 collection 累计，脚本逐文件校验不能替代该项核对。
