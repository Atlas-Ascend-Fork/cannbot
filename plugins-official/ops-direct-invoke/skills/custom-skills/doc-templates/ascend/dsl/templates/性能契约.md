# 性能契约

用于固化已确认联合寻优任务的目标、计量口径、预算与采用条件。准备挂载 `perf-opt` 时，PM 在启动前写入 `$WORK_DIR/contract/perf-contract.yaml`；已有完整契约可沿用。仅提供性能 case 时无需创建本文件，也不要求用户补寻优目标或预算；case 先保留在已确认需求与原始资料中，再由性能用例准备节点标准化进 CSV。没有用户 case 时不挂载寻优层。

本文件是寻优层的必需输入，性能采集与方案设计在文件存在时消费其已确认约束；无契约不等于无 case。字段定义引用 `ops-opmodel-toolkit` 的“冻结契约与基线”与“完整计时与必要采样”，这里只固定落盘结构。
不要求独立摸底报告。

## 必填字段

| 字段 | 内容 |
|---|---|
| `version` | 契约版本，字段或口径变化时递增 |
| `target` | 自然语言描述用户实际要求，说明适用 case、比较对象、优劣方向及适用的汇总方法；保留原始要求与确认依据，不限制为预设目标类别 |
| `cases` | 用户提供的性能 case 列表；为空表示未提供，寻优层不挂载 |
| `protocol` | 设备、缓存、编译与计时边界等共同条件，以及冻结的 `comparison` 配置与按需的 `diagnostics` 配置 |
| `budget` | 累计完整候选上限、探索轮次上限、停止条件，以及基线/探索/最终回归的开销划分与预留 |
| `framework_change_allowed` | 是否允许修改 opmodel 通用框架，缺省 `false` |
| `adopt_rule` | 正确性及本任务已确认的性能采用条件；要求改善时须有同口径稳定改善证据，不把通用改善要求强加给只要求达到指定范围的任务 |

## 结构

以下仅示范“耗时降低”的一种目标，不是所有任务必须采用的目标、阈值或汇总方法：

```yaml
version: 4
target: 端到端耗时相对基线降低 ≥10%
cases:
  - id: <case_id>
    shape: <shape 描述>
    dtype: <dtype>
    source: 用户提供 | testcase.csv:<case_id>
protocol:
  device: <设备型号与可见设备>
  cache_dir: <CANNBOTDSL_CACHE_DIR>
  compile: <编译选项与解释器>
  timing_boundary: <Task Duration 或完整设备区间>
  diagnostics:
    samples: 1
    warmup: 0
    repeat_order: case_order
    tool: msprof --aic-metrics=PipeUtilization --task-time=on --ai-core=on
    max_invalid_retries: 0
  comparison:
    samples: <已确认的每例有效样本数，至少2>
    warmup: <已确认的非负整数>
    repeat_order: <independent 或 interleaved>
    statistic: <见下文，与顺序对应>
    tool: <已确认的设备计时工具和必要选项>
    max_invalid_retries: <已确认的每例无效样本补采上限，非负整数>
budget:
  max_candidates: <已确认的累计完整候选上限>
  max_rounds: <已确认的探索轮次上限>
  accounting: <基线、探索和最终回归开销如何计入；必要复测的预留与总限制>
  stop: 达到 target 或预算耗尽即停止
framework_change_allowed: false
adopt_rule:
  - 原正确性标准通过
  - 同口径完整耗时稳定改善
  - 复测在最终交付版本上完成
```

## 约束

- `cases` 只列用户确认过的 shape 与 dtype；不得用默认 case 或按 shape 去重补齐。性能用例准备完成后按 `id` 对应统一 testcase.csv 的 performance 行，输入配方只在 CSV 维护；不得因 ID 对齐新增或改变用户场景。
- `target` 与 `budget` 由用户或 PM 决定，节点不得自行放宽或扩大。
- `protocol` 一经冻结，基线、候选实测与回归复测必须使用同一口径；确需变更时记录原因并重测受影响项。
- 模型预测值不得写入本文件的目标或结论字段。

## 迭代预算

预算在行动前确认，`max_candidates` 与 `max_rounds` 按 [性能寻优记录](性能寻优记录.md#迭代与恢复) 跨轮累计；它们不是节点重试次数或每例采样数。编译失败、精度失败、无收益和中断不退还已经使用的探索额度。一次轮次只包含事先登记的有限实验，新反馈形成的新实验另开轮，不能借最小实验或模型修正无限试验。

`accounting` 用自然语言说明基线采集、探索、待检视版本全量精度、统一检视整改回归、无效补采和最终验证的开销划分、总限制及必要预留；已有等价约定直接引用，不要求重复字段。模型搜索会话的评分请求预算与真实设备开销分别记录。预算含义不清且会影响执行上限时，PM 在启动前澄清，节点不得猜测或自行扩容。旧契约在新一轮使用前明确轮次含义和回归安排；不改历史契约或已冻结运行。

`framework_change_allowed` 只保存原授权事实，不授予本流程修改引用的 ops-opmodel-toolkit Skill 或通用框架的权限；算子模型修改沿用已有授权范围。

## 自然语言目标的对齐与验收

目标继续使用自然语言，不增加目标枚举、强制公式字段或额外的目标解析脚本。PM 保留用户原始要求及出处，在不改变含义的前提下把适用细节写清；已有上下文能够确定的直接沿用，只澄清真正的歧义、缺项或冲突，不重复征求确认。

- 比较对象说清：例如本轮冻结的自研实现，或指定版本、设备上的外部评测基线。用户要求与哪个对象比较就记录哪个，不能偷换为更容易超过的控制版本。
- 涉及数值比较时说明优劣方向；涉及比值时写明分子和分母。例如“耗时不高于基线”与“加速比不低于 1”可以一致，其中加速比须定义为基线耗时除以候选耗时。不能把“耗时不低于基线”解释为不退化。
- 按实际要求说明适用范围：逐例、全部 case 的整体结果或不同 case 族的不同条件；仅在需要时明确平均、加权、配对汇总或其他计算方法及权重来源，不能看见结果后切换算法。
- 冻结前核对 `target`、`adopt_rule`、`budget.stop` 及相关需求描述一致；区分目标是否达成、候选是否可采用、预算是否耗尽。用户确认的波动带、阈值和停止条件保留原义，不把测量不确定性擅自改成允许退化，也不因未达到额外收益幅度而否定已满足的要求。
- 未预设的新要求仍按用户原义承接；需要现有工具无法提供的测量或判断时说明具体能力缺口，不把需求判为非法、不静默改写成已有规则，也不靠文字自述放行。

执行者按已确认描述解释实测事实，verifier 独立核对计算和证据是否支持结论。有语义矛盾且无法从确认记录消除时，在启动前由 PM 澄清；节点运行中发现则保留证据并按原执行协议终止，不自行修改冻结目标。协议与样本脚本通过只证明其检查范围内的条件满足，不证明自然语言目标已经达成。

## 诊断与比较

- `diagnostics` 用于管线、任务和瓶颈观察；`comparison` 用于基线、候选及最终版本的性能对比。诊断计数器与正式计时分别标明目的，不能将插桩诊断的单次耗时直接作为稳定收益证据。优化阶段的 `opt/baseline.yaml` 索引正式控制测量和必要诊断，分别标明用途和 protocol_id，不要求预先存在一份摸底报告。diagnostics 按具体疑点选择，不是所有 case 的必经步骤；不需要时可以省略该配置。
- `samples` 是每个 case 的有效样本数；`warmup` 是每次测量序列中、该实现该 case 在计时前的预热调用数，不计入样本。`max_invalid_retries` 只限制因工具错误、数据缺失或任务无法关联而补采的次数，不用于重复到出现更快结果。上述次数与候选搜索的 `budget.max_rounds` 分开计数，不相互替代。
- `comparison.repeat_order: independent` 时，对基线和每个候选使用同一 case 顺序分别采集，用 `statistic: median` 或 `mean` 汇总每例全部有效样本。`interleaved` 时逐例交错采集基线与候选，每对带相同 `pair_id`；用 `paired_median_ratio` 或 `paired_mean_ratio` 汇总每对的 `baseline_us/candidate_us`，不能用两个独立中位数之比替代配对统计。最终复测仍与基线比较并沿用同一配置。
- 配置在看见结果前冻结。不能仅保留最快一轮、把慢样本作为异常丢弃、事后改变统计量，或用重复成功样本覆盖失败与无效记录。一次有效样本不足以支持稳定改善；重复采样只是必要证据，脚本检查通过也不自动证明收益稳定。

## 共享设备

不要求独占设备，不获取独占锁、不等待安静窗口，不因其他进程使用设备而拒收采集或降低功能验收标准。采集仍使用已确认的设备，且本任务自身按既定顺序执行，避免自行并发干扰。

使用可取得的轻量观测记录采集时间、并发情况及局限；无法观察时记 `unknown`，不能声称已独占。无需高频常驻监视、无限等待或终止他人进程。共享本身不使样本失效，也不授权挑选样本；工具错误、PMU 数据缺失或无法关联仍属于证据缺口。

有共享或波动时保留全部有效样本，按已冻结口径报告分布与影响；波动无法支持候选稳定改善时保留基线，并把候选标为证据不足。不能仅凭共享状态拒绝比较，也不能仅凭记录了共享状态就宣布测量等价；固定百分比波动带不自动抵消未知干扰。

## 校验与旧契约

PM 在挂载优化前运行 `scripts/check_perf_contract.py --contract <绝对路径> --purpose comparison`；配置了按需诊断时再校验 `--purpose diagnostics`，保存输出与退出码。输出的 `snapshot` 和 `protocol_id` 是对应用途的冻结计量身份；它包含 case 描述和共同条件，不包含候选源码 commit。源码、入口、用例版本在每份测量中独立记录。

节点使用已验收的有效校验记录；准备计时前确认实际命令遵守配置。配置与实际不一致时先处理差异，重测受影响的对照，不能选“更严格”的一方后继续沿用旧样本。

旧式平铺 `samples/warmup/tool/...` 仅能明确作为诊断消费；没有 `comparison` 配置时不能推定重复次数、统计量或稳定改善。旧 `exclusivity_policy` 字段退休并忽略，不形成独占门禁；旧采集脚本若包含等待独占逻辑须在获准的新轮中移除后使用。工具不修改历史契约、脚本、原始数据或通过状态。混用新旧采样字段或其他信息不足时，PM 在启动前确认迁移，不让执行节点猜测。

未要求性能优化或未提供性能契约时，默认流程不做性能采集，检视后直接生成文档并交付，明确未开展性能验收，不创建占位报告。脚本的无契约 diagnostics 入口仅是工具用途边界，不代表主图中存在独立诊断节点。

逐例采样记录格式和可比性检查入口见 [性能寻优记录](性能寻优记录.md#测量证据)。
