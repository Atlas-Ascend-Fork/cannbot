# 运行工具固化与预检

本插件任务中的 `scripts/check_impl_progress.py`、`check_design_evidence.py`、`check_perf_contract.py`、`validate_unit_contracts.py`、`validate_contract_consistency.py`、`review_fix.py` 由启动包装器统一提供，兼容保留的独立设计组装工具也随包供应。它们是独立脚本，不依赖安装 Skill 的相对资源布局；并不把整个源码仓复制进运行目录。

- 使用已安装 ops-direct-invoke 的 `tools/run_workflow.py --yaml <完整YAML> --work-dir <本轮目录> ...`，或其 `--template` 入口。仅调用 assemble_workflow.py 不会启动或安装运行工具。
- 启动器读取完整 YAML 和已有静态子图，发现本插件工具引用后，在 WORK_DIR/scripts 保存独立、只读副本；其他同目录文件保留。清单与预检记录在 WORK_DIR/.workflow-tools，不写 harness 的 .workflow 状态。
- 首次落盘遇到同名不同内容、目录符号链接或工具缺失时明确失败，不覆盖旧工具，不采用节点自己生成的替代逻辑。相同内容的完整文件可复用；中断后的相同副本可以继续完成固化。
- 激活已确认环境后，以 PYTHON 指定的解释器（未设置时为当前解释器）运行每个冻结脚本的 --help，检查导入和本流程所需 CLI 参数；原始输出、解释器和结果保存到唯一命名的 preflight-*.json。预检不上板、不运行测试、不安装依赖。
- 恢复时核对本轮清单、完整 YAML 身份及工具文件哈希，沿用原副本；源码仓有新版不自动更新旧运行。文件丢失、被修改或工作流身份改变时停止，不修补正在恢复的运行。需要升级或迁移时另建运行目录，保留旧记录。
- 启动预检保证派发前工具可调用，不证明算子正确、设计符合性或性能达标。运行过程中执行者仍不得修改这些验收工具；发现缺失或失效应报告并终止，不能为通过验收现场生成脚本。

这项检查仅涉及本插件的独立辅助工具。外部 Skill 脚本和需要 tasks/workflows 等相邻资源的生成器仍通过已安装 Skill 的绝对路径调用，不随意复制成孤立文件。未知业务脚本仍按自己的输入契约提供。

动态子图尚未生成时提前供应相同工具集。预检 bootstrap 也固化在本轮 .workflow-tools/bootstrap.py 并校验哈希，恢复不依赖新安装版的工具集合或参数定义；启动器保留 manifest 格式的兼容边界。前台和后台均显式传入 PYTHON，env-script 中的有效选择优先。launch-preflight-*.json 记录激活/解释器启动的输出与退出码，preflight-*.json 记录各脚本导入和 CLI 结果，失败也保留。

节点命令统一使用 `"$PYTHON" "$WORK_DIR/scripts/<tool>.py"`，避免 python3 随 PATH 或当前目录变化而选错解释器；新开 shell 按任务约定先加载本轮运行环境.sh。PM 在启动前自行校验性能契约等输入时，使用已安装 Skill 中对应脚本的绝对路径，不能假定运行目录的副本已经生成。


## 测试结果的版本绑定

使用 check_impl_progress.py 的 `--run-sheet tdd|whitebox|blackbox|performance|all --device <目标设备>` 执行固定测试入口（自动传入 --require-accelerator）。执行者与验收者须沿用相同解释器、运行环境、公开模块/入口和错误匹配器。工具在启动前归档旧结果并移除其活动绑定，执行前后核对本地源码、Unit、规格/设计、测试资产、环境事实、解释器与已记录包版本、相关环境变量；输入变化或未产生完整新结果时不绑定。红灯结果仍可记录，聚合时按逐例状态失败，不把非零退出码和旧绿灯混为通过。

原生 CSV 的分组目录同时生成 execution.json；每次执行的结果与身份记录保存在 testcase_output/.executions/ 的独立目录。默认聚合核对当前身份与 CSV 摘要，不接受无绑定、重复/缺失 case 或设备不符的行。此处保存执行证据，不是可手写的进度账本。源码或测试变化后保持已有实现，实际重跑需要的分组取得当前进度；没有只生成身份或给旧结果补签的模式。

all 模式要求基础三组非空，非空 performance 一并运行。零修复复用还须满足版本匹配；预检归档结果时保留同组 execution.json。环境身份覆盖本轮环境事实、解释器、已记录包版本和相关配置，不证明外部依赖的任意内容、实际加载二进制或运行期间硬件状态未变；这些仍由执行日志和独立验收核对。旧冻结运行不自动迁移，不改写旧 YAML、工具或结果记录。


## 逐 Unit 的 TDD 范围

实现循环使用 `check_impl_progress.py --work-dir <本轮目录> --run-sheet tdd --unit Uxx --device <目标设备>`。工具读取 Unit 的 depends_on 传递闭包，并按 CSV 的 unit_id 关联选择 active TDD 行，以转义并锚定的 case ID 正则调用固定 runner 的 --grep；不修改 CSV，不调用未选中的后续或无关 Unit。runner 必须支持该公开筛选接口并输出精确的 case 集合，缺失、多余或重复结果均失败，不静默退回全量。

同工具不带 --run-sheet、带 --unit Uxx 时，只核对该局部范围并报告当前 Unit 与依赖的逐项结果；不与全量分组门禁混用。局部 CSV 保留 runner 原生的 grep 摘要后缀，绑定为 execution-unit-Uxx.json，执行归档仍在 .executions/。版本匹配才可复用，不手写进度。局部执行前归档并撤销旧的全量 TDD 活动结果，局部通过不能替代完整 TDD 放行。

依赖失败和当前 Unit 失败分别报告；红灯是否证明当前缺失能力由原始诊断与义务独立审查，工具不靠错误字符串自动归因。共享源码影响其他已实现 Unit 时按变更补必要回归；已有完整能力修复需要覆盖全部 Unit 时，直接执行一次不带 --unit 的 --run-sheet tdd，由默认门禁聚合各 Unit，不先遍历全部重叠闭包。全部 Unit 完成后须有当前版本完整 TDD 实跑结果；同次修复已有全量通过且绑定仍有效时直接复用，否则执行上述全量入口。不合并不同版本或局部输出。最终精度、检视和交付继续执行各自的全量正确性契约。

## 已知失败的诊断与正式回归

实现迭代已有明确失败时，先用固定 runner 的 --sheet tdd --case-id <原失败ID> 或 --grep <转义并完整锚定的原case集合>，同时传 --device <目标设备> --require-accelerator，保持正式环境及完整用例语义。多例同进程批跑，避免逐例重复加载。诊断仍失败则继续定位；诊断通过再经 check_impl_progress.py 执行必要的 Unit 或全量正式回归。若触发条件依赖前置调用、用例顺序或跨用例状态，筛选必须保留它们；做不到时回到原始批次。

runner 的诊断 CSV 与全量路径分开，但它不产生 check_impl_progress.py 的正式执行绑定；保留各轮源码/用例版本、命令、退出码及原始结果，不改写绑定或把筛选结果当作正式绿灯。局部 TDD 的正式绑定和最终完整 TDD 放行仍按本轮契约执行，不要求无已知失败的运行额外做单例诊断。

## 精度修复的批次回归

precision-fix 的小范围诊断按原失败行选择 --sheet，使用固定 runner 的 --case-id 或 --grep，保持完整用例上下文；诊断不产生正式放行绑定。多类修复完成后，在该批次最终源码上按受影响分组并集分别调用 check_impl_progress.py --run-sheet <分组> --device <目标设备>，每组完整执行并绑定一次，不按类别重复整组。共享影响或状态问题需要时提前扩大检查，出现新改动时不能沿用失效结果。结果与 execution 记录按实际运行归档，不补签或拼接旧结果。此安排只合并修复阶段内部重复，precision-final 的全量验证和零修复复用边界保持不变。

## 单会话实现的 Unit 转入保护

实现仍是单个节点、同一个 Agent 会话。首次实现时，在首次编辑当前 Unit 前调用 `check_impl_progress.py --work-dir <目录> --enter-unit Uxx --device <目标设备>`。该调用不运行测试、不启动 Agent；工具读取原生 Unit 的拓扑顺序并维护 `.executions/unit-loop.json` 中的当前范围和转换引用。同一 Unit 重试为幂等操作，不清除红灯。进入下一 Unit 必须有前一 Unit 及其依赖在当前源码/输入/环境和相同设备上的正式局部全绿绑定；不接受诊断 CSV、过期结果或报告自述。不能跳过中间 Unit。

新的主 YAML 包含 --enter-unit 约定时，启动器在固定工具 manifest 记录 unit_loop_required；即使执行者遗漏首次转入，正式 TDD 入口也拒绝运行。已启用循环后，工具拒绝以其他 --unit 越序运行；最后一个 Unit 取得正式绿灯之前拒绝全量 TDD。最后一个 Unit 通过后，首次全量入口结束数值顺序循环并实际运行完整 TDD，仍须全量结果真实通过才放行。已经完成的实现保留原有局部/一次全量修复方式，不因源码变化重演所有 Unit。若确需重新打开前序能力，可显式转入已关闭的 Unit，后继顺序据此撤回并重新确认，不补造红灯。

顺序记录不代表设计约束已经通过，更不能证明文件编辑只包含当前能力。执行者仍按逐 Unit 方法核对设计承诺、到期补证和共享改动回归；最终 verifier 验收当前版本的实际实现和有效证据，不以历史编辑与红绿顺序单独否决。该工具只保护数值切换，不证明首次实现过程；不得把后补转入记录描述成过去已遵守顺序。有版本、覆盖或真实性疑点时定向追查原始记录。执行者不得手改或删除顺序记录、冻结 manifest 或工具；工具级保护不能代替文件写入权限隔离。旧冻结运行不自动启用、不改写旧工具或 YAML。

正式执行、转入和门禁命令单独调用，不能接 tail/grep/head/tee 管道或尾随命令覆盖真实退出码。进度工具把 runner stdout/stderr 合并保存到每次归档的 runner.log，保存 runner-process.json 中的原始返回码和命令，终端只显示有界尾部摘要；即使 runner 异常退出或结果无法绑定，已经返回的原始日志和返回码仍可追溯。工具0=调用成功，1=真实用例失败，2=顺序/工具/证据错误；红灯失败仅用于当前能力诊断，不允许因此切换到后继。

## DSL 版本与 API 依据

本轮 DSL 接口兼容性以已确认环境中、选定 Python **实际加载的安装版本**为准；用户明确指定版本时，实际加载身份必须匹配，存在冲突须按既有权限解决或阻塞，不能自行选择另一版本。源码仓提交、文档与样例是可追溯参考，不能取代安装身份；文档或样例中的 API 签名与选定 Python 实际加载的 DSL 不一致时，以该安装版本的公开签名为准，按其参数、顺序及关键字修正当前用法，不为匹配文档擅自升降级或切换 DSL；不固定为某个版本号，也不以“最新”作为自动升级理由。

- 环境节点在既有报告中索引解释器、DSL 包版本、模块实际加载路径及参考源码提交。分发包版本与导入模块身份不一致时如实记录并处理；不改公共环境 Skill 的 schema，不另建 API 手册或全量探测任务。
- 设计阶段确认关键方案所需能力及限制，优先用语言无关算法和数据/资源/同步关系表达，不要求提前选择 API、调用组合、地址或事件编号。实现阶段在原写集和允许范围内选用实际 API 并验证；设计中的真实 API 示例按需给出且必须正确，但示例形式不自动成为实现要求。各阶段只为本阶段真正使用的关键 API 提供适用版本证据，并复用仍有效记录。接口依据包括选定版本的导出、实际签名及配套定义；反射不可用时记录限制，使用该安装版本的公开说明、类型声明或可审查定义，证据仍不足则保持未确认，不能靠猜测补出接口。
- 文档或样例与安装接口冲突时，保留文件路径、源码提交、冲突调用及实际接口依据。在本节点权限内修正自身交付件；关键签名、参数顺序、关键字或布局表达已知不兼容时不得放行，也不能推给首个消费 Unit 再发现。仅符号同名、版本号相同、可导入或构造成功，不证明整段样例、编译能力或设备语义兼容。
- 设计约束、实现与候选使用同一版本依据。具体 API 未被公开契约或关键方案固定且实际关系可保持时，由实现者自主选择合法机制，不因与示例名称不同返回设计；关键承诺无法落实或需改变方案时按既有阻塞交接规则处理，不能自行改设计、替换底层算法或添加包装隐藏不兼容，也不擅自重装、升降级、拉取或切换环境。
- 签名核对与真实编译、设备语义验证分别记录。仅需编译或设备才能判定的能力沿用已有可行性与 TDD 义务，不因本规则新增设备实验、节点、case 或预算；验收者审查原始证据，不替执行者补跑。
- 新编排采用本规则；已启动或待恢复的运行仍沿用冻结 YAML、工具、输入与环境，不回写运行目录或热更新节点。
