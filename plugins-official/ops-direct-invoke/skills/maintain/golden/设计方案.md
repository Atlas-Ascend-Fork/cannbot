## 1. 目标与范围

工作流负责组织不同仓库、硬件、语言、任务和工程中的算子工作。差异在初始化和任务准备时确定，由脚本生成适用的技能工作区，不再让每份 Skill 在执行时识别全部组合。

首批以 CANN Bench 为默认仓库实现，同时提供 `common` 通用仓入口，用于识别目标仓自身的布局、编码与测试约定，不预设 CANN Bench 规则，也不代表其他仓库均已完成适配。硬件平台声明支持的语言；具体芯片型号和工具链仍需有实际适配与验证，平台支持声明不等于其中所有型号均已通过。

首批针对 Ascend910、Ascend950 核实能力和工具链；Ascend960 及新的 Kirin 型号作为后续适配项，不能仅因写入名称就宣布支持。工程能力按代码仓或通用仓组织，先恢复已有可验证路径，再逐项补齐适配。

TensorAPI 规划为后续独立语言/路线，与 AscendC 复用的资料归入 common。提取完成前保留 AscendC 已有的 TensorAPI 实现路线；当前只记录设计，不新增 TensorAPI 目录或声明平台支持。这里的 common 指共用资料，不是 repo-guide/common 或 engineering/common 的实现，也不表示自动合并父级 Skill。

本轮先做上下文隔离：每个 task 的 execute/verifier 使用独立会话、启动目录、身份和技能集合。代码与证据通过明确路径访问，不承诺操作系统级的文件、进程、依赖或设备资源隔离。

## 2. 六类差异与确定时机

| 维度 | 主要内容 | 通常确定时机 | 作用 |
|---|---|---|---|
| 仓库 | 仓库位置、规范、接口和交付约定 | init | 选择 CANN Bench 实现或通用仓入口 |
| 硬件 | Ascend/Kirin 平台、具体型号及所需开发方式 | init | 声明语言支持范围、环境和硬件能力 |
| 用户 | 问卷偏好、自主决策范围、额外人工检视点 | init | 配置交互方式与人工门禁 |
| 语言 | AscendC、CANNBot-DSL，后续 TensorAPI | 需求分析 | 选择开发、检查与验证能力 |
| 任务 | 算子开发、用例开发、性能优化等 | 接收任务与需求分析 | 从生成的引导选择 workflow 模板 |
| 工程 | 对应代码仓或通用仓的工程布局与接入方式 | 需求分析 | 确定构建和测试入口 |

仓库与工程是不同维度，不能用仓库名隐含决定所有工程细节。硬件同时记录平台系列和具体型号；语言支持以平台声明为基础，再核对该型号、工具链和工程是否具备所需能力。

一个运行实例固定一组选择，不在执行中替换组合。新任务可以重新选择语言、任务和工程；仓库或平台发生变化时重新准备对应配置。缺少关键选择、组合不支持或能力缺失时，在启动前报告，不静默回退到另一平台、语言或工程。

用户偏好可以减少重复问卷，并授权模型在指定范围内决策；不能把偏好当成当前任务事实或新增修改权限。已有明确答复继续沿用，未答复不算确认。

用户指定的人工检视点在启动前落实到本轮图的审批配置，使用 core 的公开审批机制，决定和待答状态可恢复；不能仅靠提示词要求 Agent 记得停下来。运行后新增检视点按调度机制处理，不直接改写正在执行的冻结图。

## 3. 分层与能力组织

| 层次 | 职责 | 不承担的内容 |
|---|---|---|
| 主 Agent 入口 | 源码位于 skills/orchestrator，工作区以 ops-direct-invoke 承接需求对齐、模板选择、准备输入、启动和交付 | 具体语言、平台和任务的内部步骤 |
| 身份层 | 架构师、开发者、验收者及必要编排身份的职责与权限 | Skill 清单、领域教程、模板路由 |
| Skill 能力层 | 仓库约定、平台知识、语言方法和工程操作 | 自行识别全部组合、控制外层调度 |
| task | 当前任务的输入、输出、执行和验收契约，分别声明所需能力 | 决定公共能力的内部文件布局 |
| workflow | 节点依赖、预算、角色及模板适用说明 | 复制 Skill 实现 |
| 工作区生成器 | 根据已确定选择解析能力、检查完整性并生成工作区 | 替用户做尚未确认的业务决策 |
| harness core | 在指定上下文中启动 Agent，管理执行、验收与恢复 | 识别仓库、平台或语言，选择业务能力 |
| dsh 展示层 | 展示配置、运行状态、证据和交互入口 | 维护第二套调度状态或绕过 core 执行 |

主入口只描述框架如何调度。模板何时、如何使用只写在 `use_when`，脚本生成 workflow 引导供主 Agent 选择；平台、语言声明只用于组合校验和能力绑定，不成为另一份模板选择规则。

### 3.1 重组现有 repo-* 能力

不保留按七个 repo Skill 逐个复制所有差异的方式，也不将它们合成一个包揽所有知识的大 Skill。按实际共用内容和职责重组为以下分组：

| 能力组 | 原有内容的处理 | 差异来源 |
|---|---|---|
| 需求对齐 | 原 repo-requirement 重写为 requirement；按平台选择，在同一实现中确定语言、任务、工程与用户要求 | 平台；仓库规则由 repo-guide 提供 |
| 环境 | 以 env-check 组织环境记录、候选发现和授权复用规则；分别提供适用的检查方法 | 平台、工具链、语言和工程 |
| 仓库指南 | 以 repo-guide 合并 repo-knowledge、repo-coding-rules 与 repo-test-develop，维护仓库事实、编码约束、测试框架、用例接入和回归要求 | CANN Bench 实现或 common 通用仓入口；条款注明适用范围 |
| 工程开发 | 以 engineering 合并 repo-build-guide 与 repo-op-templates，提供骨架、接入和构建方法 | 按代码仓或通用仓分组，校验语言、平台和实际工程 |
| 文档模板 | 以 doc-templates 统一提供知识、测试、检视与验收等报告模板 | 平台和语言 |
| 语言领域能力 | 复用已有 AscendC、DSL 能力，必要时新增 dsl-* 等技能族 | 语言和实际任务 |

能力接口按职责划分，各自明确选择维度。requirement 只按平台选择，语言、任务、工程和用户偏好是同一平台需求 Skill 要确认的信息，不再决定另一份 requirement 实现；仓库规则由 repo-guide 提供。环境涉及平台、语言、工具链和工程；仓库指南按仓库选择，其中的具体条款也可能有语言、工程或平台适用范围；文档模板按平台、语言选择。

engineering 分为 cannbench、cannbot-dsl、common 和 kirin-common；common 承接原 ascendc-direct，kirin-common 承接 Kirin 专用工程和测试框架接入。DSL 工程在执行时读取调用方提供的固定版本官方 cannbot-dsl samples，不预写未经确认的布局或命令。CANN Bench 指南目前仅适配 Ascend；Kirin 使用通用仓库指南，初始化和运行准备均拒绝未适配组合。

测试框架通常由仓库固定，测试知识归入 repo-guide，不再独立设置测试开发虚接口。仓库指南说明用例如何设计、接入和执行，需要哪些回归、精度标准与证据；实际构建和测试由 task 下发执行，独立验收仍由 verifier 承担。设备或 Simulator 等运行差异在适用资料中说明，不能把 Kirin 这样的硬件平台当成仓库变体。

能力组不强制等于一个 Skill；资料多时按职责分开、按需读取。仓库约定不能强迫 DSL 遵守仅适用于 AscendC 工程的包装方式，通用测试原则也不能混入某个工程专用的命令。

### 3.2 来源、绑定和覆写

维护通用规则、仓库、平台、语言和工程的能力来源，由声明明确每项能力最终采用哪个实现。平台在自己的声明中列出支持语言；节点按 execute/verifier 分别声明所需能力，外部 Skill 保留真实名称和公开契约。

实现选择按各能力声明的选择维度匹配；requirement 仅按平台，环境和工程能力按其实际组合匹配。选择声明明确实现所处阶段、适用组合及必要版本约束；不能从路径中缺少某个维度推断它对该维度通用。多个实现同时匹配或没有完整匹配时报告配置缺口，不按目录顺序选取、不将两个各自通过的局部检查当成组合兼容性已通过。

例如 env-check 在 init 阶段先按已确定平台收集候选与基础事实；语言和工程确定后，再选择并链接覆盖实际组合的末级 Skill，例如 `env-check/ascend/ascendc/`。初始化所需的基础发现方法由平台资料提供，不将平台分类目录当作独立 Skill 链接。完整检查必须同时考虑平台工具链、语言依赖及其兼容性，复用仍有效的基础证据。基础检查通过不等于最终环境就绪，语言检查也不能覆盖掉平台约束。

覆写只发生在生成的工作区中，不修改共享 Skill 的源文件。每个逻辑能力只有一个明确的最终实现，生成器选择并整体链接对应的实现目录，不在运行时拼接多份 Skill 正文；repo-guide 的 common 与 cannbench 也是二选一，不自动叠加。共用资料由各实现引用单一来源。来源冲突、同名重复或必需资源缺失时报错，不靠目录扫描顺序决定优先级，也不在运行时让 Agent 再选一次。

不建立所有维度组合的完整副本。通用资料维护一份，只有存在真实差异的部分提供实现；确有交叉差异时为实际支持的组合补充适配。通用仓入口不替代目标仓的实际能力验证。

多态能力集中在 `skills/custom-skills/` 下，借用面向对象中虚函数的概念；按能力及适用条件分类，短名末级目录直接包含 SKILL.md，例如 `env-check/ascend/dsl/`，不再增加完整名包装层。这些实现目录已填充；同能力的不同变体使用相同的元数据 name，选取条件由分类与声明表达。

当前已建立需求、环境、仓库指南、工程和文档模板五类定制能力目录，测试开发知识归入仓库指南，工程能力负责实际框架接入。doc-templates 与 env-check 采用相同的平台/语言分层；不预建全部维度组合。共享领域 Skill 与独立性能工作流继续通过外部依赖复用，不复制其内部实现。

各目录的职责、分类与适用范围在对应 README 中说明。目录名不等于适配通过声明，填充前仍须明确并验证具体芯片、工具链与工程条件。最终直接链接选中的末级 Skill 根，不链接上层分类目录或自动叠加父目录正文。

安装或生成工作区时选择末级 Skill 根，复用源码安装已支持的显式路径按 name 链接能力；同一能力的同名变体不能同时注册。SKILL.md 的 name、任务调用名称和工作区注册名保持一致；主入口为 ops-direct-invoke，其余本插件 Skill 使用 ops-direct-invoke- 前缀。不要求源码目录 basename 与其相同，也不在安装时改写 Skill 正文。maintain、orchestrator 保持现有布局，golden 不再迁移。

原 scripts/ 的运行工具归入 tools/，测试专用脚本归入 tests/helpers/，运行链路不能依赖 tests/。报告模板归入 doc-templates 的各平台、语言实现，各自维护实际使用的完整模板，不设 common 或跨实现模板链接；外部 Skill 原生产物沿用其契约。maintain/golden 只存需求与设计基准。运行工具及协议通过 OPS_DIRECT_INVOKE_ROOT 等明确路径提供给节点，同步修改旧的 scripts/、references/ 和相邻 Skill 路径推导，不为读取运行资料而加载 PM 或维护身份。外部技能按需链接，保留其公开契约。

现有自动发现只扫描 skills/ 第一层，短目录不会使安装器自动发现所有变体。npm 打包沿用公共规则，通过插件资产声明保留全量候选及 tools、orchestrations 及配套资料；插件初始化入口再按元数据 name 注册所选 Skill 集合。源码 init 与 npx 安装命令需进入同一交互初始化入口，不要求用户另行手动配置；初始化与打包共用这份声明，未选变体作为资产保留。

## 4. 两阶段准备与运行工作区

### 4.1 init：确定仓库、硬件和用户偏好

保留主线 README 的命令语法，不新增必填参数，已有 --target、--skills 等选项的语义继续适用：

```bash
npx @cannbot-plugin/cannbot install ops-direct-invoke --tool opencode
bash plugins-official/ops-direct-invoke/init.sh project opencode /path/to/your-workspace
```

命令执行后，由同一初始化问卷采集仓库、平台、用户偏好等新增选项；语言、任务和工程仍在需求阶段确定。复用有效显式参数和已有答复，展示问卷前形成实际待问列表，以本次总数 N 逐项显示 `(1/N)` 至 `(N/N)`，不硬编码题数。源码与 npm 共用编号问卷；非交互环境通过已有配置或 CANNBOT_DIRECT_INVOKE_CONFIG 指定 JSON 文件提供已确认选择；插件 init.sh 也支持 --init-config。

1. 根据参数、已有记录和问卷确定目标仓库、硬件平台及已知型号，记录来源和用户偏好。
2. 读取平台支持声明，按平台选择 requirement、按仓库选择 repo-guide，准备主 Agent 能力。开发语言尚未确定时，只记录平台基础检查范围，不预加载全部语言的开发技能，也不宣布最终环境已就绪。
3. 将共享技能、身份文件和依赖作为可定位的资产准备好。资产可供生成器读取，不代表全部注册到主会话的技能目录。
4. 生成项目配置。重复初始化只更新本工作流管理的内容，保留用户文件和其他插件配置，不改写已经运行的工作区。

### 4.2 需求分析结束：确定语言、任务和工程

需求分析仍由主 Agent 在当前用户会话完成，使用 init 选定的平台 requirement，并从 repo-guide 获取仓库规则。在同一平台需求 Skill 中确定最终交付语言、任务、工程等信息，不切换另一份语言 requirement。语言确认后绑定适用的环境与开发能力，补齐完整环境检查；不要求用户选择所有内部实现细节。环境就绪结论必须覆盖所选实际组合，不能只提供单独的语言或平台通过记录。

确认后记录六维选择、授权、环境、代码与交付位置。生成并读取 workflow 引导，选择适用模板，检查模板所需能力和输入。确定语言后若当前客户端不能动态刷新技能列表，主 Agent 可直接读取本阶段所需资料；不以刷新会话为由要求用户重复回答。

随后创建独立的 workflow 目录，冻结配置、模板和能力版本，交给 harness。已存在的运行目录不覆盖；改变组合应新建运行实例。

### 4.3 每次 task 的 execute/verifier：生成节点上下文

示意布局如下，具体客户端目录由适配器生成：

```text
<项目>/
├── <主会话技能目录>/             # 编排、维护、需求与仓库指南
└── .cannbot/
    ├── <共享资产与依赖>/         # 不全部暴露为主会话 skills
    └── <任务>/workflow1/
        ├── 需求分析.md
        ├── 环境信息.md
        ├── workflow.yaml
        ├── context.json          # 本轮选择、路径、来源与摘要
        ├── run-inputs.json       # 已物化任务图的固定摘要
        ├── .context/             # 本轮固定资源副本
        ├── .workflow/            # harness 管理的状态
        ├── code/                 # 需要独立代码工作区时使用
        └── agents/
            └── <task-id>/
                ├── execute/
                │   ├── AGENTS.md
                │   └── <客户端技能目录>/
                └── verifier/
                    ├── AGENTS.md
                    └── <客户端技能目录>/
```

节点 cwd 指向自己的 execute/verifier 目录，`WORK_DIR` 始终指向本轮产物目录，`CODE_DIR` 指向实际代码目录。任务输入、报告、工具和裁决回调使用明确路径，不将切换 cwd 变成业务产物迁移。并行代码修改继续使用独立 worktree 等代码版本机制，技能隔离不能替代代码合并和集成验证。

节点工作区包含对应身份和本阶段需要的 Skill。`AGENTS.md` 链接到身份层文件；需要其他指引文件或命名角色配置的客户端，由适配器生成等价入口。执行者与验收者使用独立会话；重试可以复用阶段目录内的固定身份与技能，但每次新建会话并保留原始证据和尝试记录，不继承对方会话。

根工作区不注册所有开发、测试和性能技能。节点也不整体链接根目录的客户端配置，避免把主入口、其他语言和无关角色再次引入。允许继承的基础模型、连接配置与业务技能分开处理，不复制凭据到运行清单。

客户端可能自动加载祖先目录、用户级 skills 或全局插件，必须通过实际客户端检查可见上下文；不能仅凭目录中链接正确就宣布隔离完成。本轮目标是控制本工作流主动注入的上下文，不修改用户全局配置，也不声称强制禁止节点读取其他文件。

### 4.4 版本、重试与恢复

本轮清单记录选择、代码路径、模板版本、身份和技能来源、固定版本及必要内容摘要。运行中不随上游仓更新重新链接。软链接只能指向本轮保留的固定来源；不能冻结版本号却仍指向会变化的开发目录。不能可靠固定来源时生成本轮副本。

同一轮重试、恢复复用清单和技能快照。来源丢失或内容不符时明确阻塞，不自动换到最新版。人工检视决定和已使用预算仍由原调度机制恢复；旧运行保持原版本，新旧状态不强行互转。

源码版本管理与 Skill 快照分开：沿用现有 code_versions 和 review_fix 能力，工具迁入 tools 后保留代码 SHA、冻结输入、证据验收、恢复提交和历史交付契约。恢复提交需重新验证，不复用旧 SHA 的通过登记；检视修复仍按 core 预算决定重试或基线托底。harness 的目录快照恢复与显式 Git restore 是不同机制，不能互相代替或混用。

## 5. 对 harness core 的接口要求

主线已支持动态子图：依赖通过后读取子图文件，以父/子完整 ID 注册并派发任务。沿用现有 `task_executor(entry, work_dir, session_path)` 回调，在每次实际派发前准备阶段 cwd、身份和 Skill，覆盖运行中生成的节点；不重做发现与调度。适配器从本轮清单和 core 状态取得以下信息：

| 输入 | 含义 |
|---|---|
| task 标识、阶段和尝试标识 | 区分 execute、verifier 与重试记录 |
| Agent 工作目录 | 当前阶段的实际 cwd，并同步正确的进程工作目录环境 |
| 身份来源 | 当前角色的身份文件或客户端角色配置 |
| 技能集合及资源位置 | 由工作流解析好的能力清单，不由 core 推导业务组合 |
| 共享路径 | WORK_DIR、CODE_DIR、必要输入与裁决接口 |

由直调工作流解析业务能力并准备节点工作区，通过现有回调启动 Agent；保留 core 主调度、共享 WORK_DIR、会话日志和裁决接口。默认 runner 当前使用同一 work_dir 作为 cwd/PWD，新接入需同步设置实际阶段 cwd/PWD；上表是适配器所需信息，不代表回调已经直接提供全部字段。

保持 goal、acceptance、out_of_scope 双方可见，approach 只给执行者、procedure 只给验收者。日志、裁决、重试、回滚和人工审批沿用 core 的单一状态来源；改变节点 cwd 后必须验证这些接口仍定位正确。

## 6. 性能优化工作流

提供已有算子的纯性能优化入口，以及完成开发与原用例验收后进入性能优化的组合模板。模板适用场景只在各自 `use_when` 中维护。

性能执行 task 负责接好原工作流需要的源码、用例、目标、环境、对标来源与输出位置，调用实际安装版本的 `ops-perf-optimize-workflow`。安装与资产准备复用原插件的声明和初始化能力，不在直调中列举并维护其全部内部 Skill。

原工作流的调度、配置、轮数与停止条件按其公开契约执行，直调不改写内部流程。需要编排权限时使用对应身份，不扩大普通开发者权限。外层 execute/verifier 隔离；本轮不改造原性能工作流内部的 Agent 隔离方式，但须保证其公开入口所需配置仍完整可用。

外层 verifier 根据最终版本和原始证据确认原用例是否全通过；不重复原性能工作流的内部验收，不用优化前的通过记录代替最终版本证据。保留原工作流恢复点和输出，内部未完成时如实交付，不重置预算后伪装成续跑。

## 7. 知识积累、检索与回流

本地知识分成可共享知识的消费快照和当前项目积累的知识卡片。优先复用已有知识仓的格式与公开工具，先核对契约，再确定存储接口；不在本轮预设新的数据库或向量服务。

知识卡片至少记录主题、适用仓库/工程、平台与具体芯片、语言、成立条件、结论、来源、验证状态及证据版本。区分已验证结论、上游资料和待验证假设，不能将一次失败猜测直接写成通用规则。

检索先按组合和适用条件过滤，再按问题关键词或现有索引检索，返回少量摘要与来源，按需读取正文。优先考虑精度、召回和上下文开销，只有实测不足时再引入更复杂的索引方式。知识作为参考，不能改写本轮确认需求、冻结设计和验收标准。

任务结束后提炼候选卡片并在本地保留；不要求每个执行节点都带上知识维护技能。主 Agent 或独立回流任务负责去重、复核适用范围和证据，符合价值与共享要求的内容再按已授权流程提交知识仓，不能默认发布用户私有代码或数据。

本地库可以在任务间动态更新，本轮消费的知识版本保持可追溯。检索记录保留所用卡片版本与来源，使后续能够判断经验是否仍适用。

本轮知识搜集产物和新实验结果仍可作为任务证据交给下游节点；知识快照约束的是外部知识来源的隐式更新，不阻止图中声明的正常产物交接。

## 8. 维护框架与测试

建立独立、可单独运行且有统一入口的维护测试体系。测试不混入普通算子执行上下文；维护资料记录分层、职责与变更原则，业务用法和当前模板清单由实际模块维护。

| 验证层次 | 主要验证内容 |
|---|---|
| 配置与生成测试 | 六维选择、平台语言声明、多维联合匹配、基础检查与完整检查的区分、冲突与缺项、工作区生成、版本冻结和用户文件保留 |
| 调度接口测试 | 静态与后生成节点 execute/verifier 的 cwd、身份、技能与输入可见性，以及报告、裁决、代码版本与恢复接口 |
| 安装与打包测试 | 原有 init/npx 命令及选项兼容，交互入口一致、问卷编号和总数准确且复用有效答复；根目录仅暴露适用技能，资源完整、链接有效，注册名与元数据一致，未选变体不自动暴露，重复安装不污染已有运行 |
| 真实客户端验证 | 检查实际加载的身份、祖先/全局配置影响与节点上下文，而非只检查文件存在 |
| 业务与设备验证 | 按已声明组合验证开发、用例开发、性能接入和最终原用例；明确真实设备与 Simulator 的结论范围 |
| 知识与展示验证 | 适用条件过滤、来源可追溯、候选回流及 dsh 展示与原状态一致 |

测试聚焦稳定契约和可复现行为，不锁死模板数量、节点数量或提示词措辞。core 内部调度正确性由 core 的测试负责，插件只验证自己的接入。模拟测试通过不能代替真实 Agent、设备功能或性能通过。

测试环境与用户任务分开，测试后删除临时目录。发布前运行完整维护回归及受影响的仓级安装、打包检查；不以跳过失败项目宣布版本可用。

## 9. cannbot dsh 适配与可视化

dsh 作为客户端适配目标，使用相同的任务、能力清单和运行状态，其任务执行入口也需接入相同的阶段工作区准备逻辑。核对指引加载、Skill 发现和 Agent 启动接口后实现最小贯通路径，不假定存在尚未确认的插件 API。

优先提供以下展示能力：

- 当前仓库、平台/芯片、语言、任务、工程与用户交互偏好，以及组合不支持的原因。
- workflow 节点、execute/verifier 进度、重试、阻塞与待人工检视事项。
- 节点实际使用的身份与技能来源、代码版本、交付件和原始证据链接。
- 性能工作流公开进度及结果入口、知识卡片命中与来源。

先提供可供终端或界面消费的稳定结构化信息，再按 dsh 能力增加交互视图。审批操作通过 core 的公开接口提交，展示层不直接写状态文件；不依赖 UI 的用户仍能通过命令行完成任务。

## 10. 分步建设计划

| 阶段 | 工作内容 | 完成依据 |
|---|---|---|
| 0：需求与设计 | 清空旧插件目录，保留需求原文并讨论本方案，建立目录骨架与简短目录说明 | maintain/golden/ 保留两份基准文档，Skill 分组有 README、实现待填充；需求项均有设计归属 |
| 1：配置与能力来源 | 确定六维声明格式、平台语言支持、能力分组、版本清单和目录布局 | CANN Bench 默认组合可解析，未知组合和冲突明确报错 |
| 2：初始化与需求入口 | 恢复插件身份与安装声明，生成主 Agent 的最小技能集合，完成两阶段需求准备 | 源码与 npm 安装行为一致；语言确认前不注入全部开发能力 |
| 3：节点工作区 | 通过现有 task_executor 接入阶段工作区和客户端适配，落实身份、技能、cwd 与共享路径 | 静态与动态节点 execute/verifier 独立启动；裁决、并行、重试与恢复保持有效 |
| 4：业务模板 | 从最小完整开发链路开始，逐项恢复 AscendC、DSL、Kirin 与用例开发，接入纯性能及开发后性能模板 | 每项声明支持的组合都有对应能力、完整链路和验证记录 |
| 5：知识闭环 | 本地卡片、条件检索、任务后提炼及知识仓回流接入 | 检索结果适用且可追溯，新增知识不污染正在执行的快照 |
| 6：展示与发布 | dsh 最小接入、可视化、完整回归、文档和市场入口同步 | 展示与 core 一致，安装打包完整，发布范围与验证范围一致 |

维护测试从阶段 1 起随接口建设，不留到最后集中补齐。各阶段分别检视，再继续填充目录；不一次性恢复全部旧文件，也不把旧实现中的隐含规则原样带回新 Skill。

重建期间仓级入口可能仍引用已移除文件，这是当前草稿分支的已知状态。在恢复可安装能力前同步市场索引、安装来源、打包与文档，避免用旧的 dist 缓存掩盖缺失；不得将仅含设计文档的分支直接发布。

## 11. 实施前需要核实的接口

目前业务边界已足够开始建设，下面是实现调查项，不是重复要求用户确认：

1. 现有 task_executor 与各客户端执行入口如何接入同一阶段工作区准备逻辑。
2. 各客户端的本地与祖先指引、全局 Skill 加载规则，以及命名角色与身份文件的实际衔接方式。
3. CANN Bench、官方 DSL samples、通用仓与 Kirin 工程的适配依据，以及具体型号和语言组合，先验证后登记支持。
4. 性能工作流、知识仓和 dsh 的实际公开接口与版本，分别复用其原生能力。
5. 按元数据 name 打包并保留全量候选和共用资源，以及源码/npm 共用的交互初始化与选取入口。

这些调查的结论应更新对应模块设计和支持声明。确有新的业务取舍时再集中确认，不以新增配置项或提示词分支掩盖未解决问题。
