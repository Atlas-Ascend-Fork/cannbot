# 定制 Skills

## 模块范围

插件 `skills/custom-skills/` 下的能力，构成工作流面向具体算子仓、平台和语言的知识与工程能力层。task 通过稳定的 Skill 名称引用它们，实际内容由目标仓提供。

## 设计思想：父仓与子仓的知识分层

一些算子仓会把本工作流安装到自己的项目内。不同仓的构建、编码约束、领域背景和测试框架并不相同，不能要求所有仓使用同一套仓库知识，也不应为适配每个仓复制一套工作流。

这里参考面向对象的“基类与子类”思想：

- **父仓（基类仓）**：维护通用工作流、角色和 task，并提供默认的 `ops-direct-invoke-*` Skill 实现。
- **子仓（具体算子仓）**：复用工作流，以同名 Skill 替换默认实现，提供本仓知识与工程方法。
- **稳定名称是能力接口**：task 仍引用 `ops-direct-invoke-engineering`、`ops-direct-invoke-repo-guide` 等名称；安装后的同名 Skill 决定这些任务如何适配当前仓库。

这是能力契约和知识维护上的继承关系，不是 Git 仓库继承，也不是运行时自动合并两份 Skill 正文。同名替换后，以实际安装的 Skill 内容为准；子仓需要保留的默认内容由子仓显式维护，不能假设父仓规则会自动叠加。

```text
父仓：通用 workflow / task → 引用稳定的 ops-direct-invoke-* 名称
                                      ↓
                  默认实现 或 子仓提供的同名实现
                                      ↓
                  当前算子仓的知识、构建与验证方法
```

父仓维护工作流机制，子仓维护本仓事实。子仓新增或调整本仓知识时，应落入对应 `ops-direct-invoke-*` Skill，避免把仓库特例写回通用 task、PM 入口或公共领域 Skill。

## 为什么采用 SOLID 原则

| 原则 | 设计目的与维护边界 |
|---|---|
| 单一职责 | 每个 Skill 负责一个知识或工程能力域，使一种知识变化只需修改一个归属明确的位置。仓库知识、工程实现与环境检查分别维护，各自的共用资料保留单一来源。 |
| 开闭原则 | 仓库差异通过同名能力扩展，避免每接入一个子仓就修改通用编排。通用流程自身的演进仍由父仓维护，不能借覆盖仓库知识改变调度和角色边界。 |
| 里氏替换 | 子仓实现保持逻辑名称、职责和约定的输入输出，让调用方无需识别实际实现来自哪个仓库。替换不得悄悄删去调用方依赖的能力。 |
| 接口隔离 | 子仓只覆盖需要定制的 Skill，其余沿用默认实现；不能为了替换一个 Skill，要求复制或重写整套能力。单个被替换 Skill 的内容仍须完整，不自动合并父仓正文。 |
| 依赖倒置 | task 依赖抽象能力契约，不指定子仓 Skill 的章节结构、内部路径或实现方法，使不同仓库能独立维护。 |

### 为什么兼容责任是双向的

子仓替换不能破坏调用契约，父仓演进也不能随意破坏已接入子仓的覆盖实现。已发布的能力名称、输入输出与调用约定应保持兼容；扩展优先采用不改变旧含义的方式，新增可选配置应有明确默认行为。确需破坏性调整时说明受影响的调用方和子仓、提供迁移办法，不能让旧覆盖静默失效，也不为尚不存在的消费者预设兼容层。

### 为什么知识需要单一来源

仓库事实由仓库维护，Skill 负责帮助 Agent 定位和使用这些事实。开发者同样需要的编码规范、测试框架和领域说明，优先存放在仓内共享文档；Skill 引用权威原文并补充必要的任务指导，避免复制出第二套会独立过期的知识。

仓库知识围绕自身职责组织，不写死调用角色、工作流阶段或前后节点。跨 Skill 的组合由 task 或 PM 声明；引用仓内资料不意味着把其他 Skill 的内部规则复制进来。

## 仓库能力的正交职责

| Skill | 设计目的与应包含的内容 | 职责边界 |
|---|---|---|
| `ops-direct-invoke-repo-guide` | 介绍本仓特殊的领域背景、编码约束及测试框架，说明用例如何编写、接入和执行，以及变更需要的验证和证据 | 按仓库选择；工程骨架和构建归 engineering，环境前提归 env-check |
| `ops-direct-invoke-engineering` | 提供新增算子所需交付件的组织方式，说明如何从源码、配置和依赖构建出所需产物 | 按工程及其支持声明选择；不能将构建成功等同于验证完成 |
| `ops-direct-invoke-env-check` | 介绍开发所依赖的环境，以及如何确认环境具备开发条件，例如工具链、依赖、设备与必要配置 | 按平台、语言选择，并核对本轮工程；环境可用不代表产物构建成功或功能通过 |
| `ops-direct-invoke-requirement` | 引导 PM 对齐需求，提示应确认的接口、范围、约束和交付标准 | 按平台选择，语言是需求输出；不替用户决定未确认事项，不代做方案设计或执行验证 |
| `ops-direct-invoke-doc-templates` | 提供工作流报告的格式模板 | 按平台、语言选择；不承担业务判断或调度 |

需求层记录用户选择的解释器、工具链与修改权限，环境层提供候选事实并验证被选中的组合。环境缓存按实际组合、语言和依赖范围复用，不能把通用设备检查等同于所有语言均已就绪，也不能把缓存中的旧授权带入新任务。已确认任务的恢复沿用约定，只补查变化部分。

工程交付件模板由 engineering 维护，工作流报告格式模板由 doc-templates 的各平台、语言实现独立维护。各实现只携带自身实际使用的完整模板，不设置 common 模板目录，也不链接其他实现的模板；外部 Skill 已有的产物格式继续遵循其原契约。平台以 `platform.json` 声明支持语言，工程以 `support.json` 声明支持组合；声明不能替代设备与工具链验证。

例如，BLAS 算子仓涉及标准语义：标准背景与仓库约定应归入该仓的 `ops-direct-invoke-repo-guide`，而不是散落在构建、编码和测试说明中。

## 维护方法

### 判断知识归属

先判断改动属于通用工作流机制、跨仓领域能力，还是当前仓库事实。当前仓库事实按上表落到唯一负责的 `ops-direct-invoke-*` Skill；多个 Skill 使用同一事实时，保留明确的归属，不复制成多套独立规则。需要组合多个 Skill 的任务，由 PM 或 task 显式绑定。

新增条款时检查是否侵入其他 Skill 的职责。例如，测试执行命令与回归覆盖要求应由 repo-guide 维护，不在 engineering 重复维护另一套规则。

### 同名替换与安装

同名替换保留 task 面向的能力接口，同时改变知识来源。子仓实现应保留对应名称，并提供完整说明及所需资源，不能只写一段补丁并假定未提供的内容会自动从父仓继承。当前安装覆盖支持 requirement 和 repo-guide；其他能力按声明选择完整实现。具体安装参数见初始化配置 `asset_root` 所定位的插件 `README.md` 中“工作区资产与定制”。

覆盖后核对实际安装路径、软链接或副本指向子仓实现，且 task 引用的名称仍可解析。保留能力契约：例如 engineering 仍说明如何构建产物，repo-guide 仍给出测试接入与完整验证方法。具体路径、命令和框架可以因仓而异；与 task 约定的输入输出不兼容时，必须显式处理，不能靠同名掩盖缺失能力。

子仓局部知识调整不应直接改动指向父仓源码的软链接目标，以免影响其他工作区；应维护子仓自己的实现并通过安装覆盖机制选用。新增 Skill 或在 task 中引入新的 Skill 名称时，仍遵循入口中外部来源注册与插件内自动发现的规则，并确认工作区实际可加载。同名替换已有 Skill 无需重复创建同名注册项。

### 验证与同步

修改后按该 Skill 的实际职责验证：构建指南核对构建入口与产物，模板核对交付件结构，测试指南核对接入、执行及回归证据要求，需求 checklist 核对信息是否足以支持后续规划。不能仅凭文档可读取就认定能力适配完成。

若改动涉及稳定名称或输入输出契约，同步检查 task、workflow 及其他消费者；若只是子仓内部实现变化且契约不变，保持通用工作流不受影响。

末级目录直接包含 `SKILL.md`，同一能力的变体使用相同元数据 name；初始化或本轮准备只绑定所选完整实现。必需依赖使用 `metadata.required_skills`，节点条件能力由阶段声明提供。每轮冻结后不随来源更新，恢复沿用同一副本。
