# Task 组织与节点字段规范

## 字段语义与可见性

| YAML 字段 | 含义 | 执行者可见 | 验收者可见 |
|---|---|---|---|
| `goal` | 本节点的总体目标 | 是 | 是 |
| `approach` | 执行者的执行方法 | 是 | 否 |
| `procedure` | 验收者的验收方法 | 否 | 是 |
| `acceptance` | 双方共同确认的交付件清单 | 是 | 是 |
| `out_of_scope` | 本节点禁止的操作 | 是 | 是 |

可见性是硬边界：`approach` 只下发给执行者，`procedure` 只下发给验收者。双方都需要的信息只能写在 `goal`、`acceptance`、`out_of_scope` 中，并遵循各字段语义；写在对方不可见字段里的约定等于不存在。

## 为什么只下发必要信息和权限

节点应获得完成本任务所需的输入、相关约束、Skill 和证据路径，避免把整段会话、其他算子信息或无关全局上下文注入任务。最小信息不等于缺少契约：双方需要的约定必须在共享字段中完整表达。

写入范围和操作权限以任务需要为限，避免无关代码、上游交付件和调度状态被误改。权限应结合具体任务配置，不能把“开发者不得修改测试”之类的阶段特例写成身份层的永久限制。

每个节点有明确交付件和可判定的完成标准，使下游不必猜测任务是否完成。交付件放在 `acceptance`，内容判定放在 `procedure`，不为可观测性重复注入对方不可见的内部方法。

## 1. 无条件信任上游产物，不做重复校验

上游交付件在流入本节点前已由上游节点的验收者验收通过。本节点直接使用，不对其内容重新校验；使用前只确认产物存在且可读取。若使用中发现上游产物缺陷，按第 3 条就地终止并说明，不在本节点补做上游的验收工作。

## 2. goal 只写目标，保持简短

`goal` 只回答“本节点要达成什么”。不写执行方法、交付件清单或验收标准，它们分别属于 `approach`、`acceptance` 和 `procedure`。

自检方法：`goal` 中一旦出现具体步骤、文件名或判定条件，说明写多了，应移入对应字段。

## 3. 问题就地解决或就地终止，不得后移

本节点发现的问题（输入缺陷、环境阻塞、能力缺失）由本节点闭环：能解决的当节点解决并记录证据；无法解决的按执行协议终止本节点，将证据写入本节点报告。禁止绕过问题继续交付，禁止把问题留给下游节点处理。

### 就地处理不能越过上游决策边界

上游设计可能包含当前节点未持有的约束，因此本节点可以复现问题、缩小范围并给出根因证据，但不能擅自改动已确认的架构、接口或实现策略。就地解决仅限当前任务及权限范围；需要改变上游决策时终止本节点并报告，由 PM 通过 harness 安排负责该决策的角色处理，不带着已知缺陷继续向下游交付。

## 4. acceptance 只列交付件和存在性检查

`acceptance` 是执行者与验收者共同接受的交付件契约。为防止重复验收，只写交付件清单及其存在性检查，每条给出可直接执行的测试指令，例如：

```bash
test -s "$WORK_DIR/{{id}}-测试执行记录.md"
```

不写内容正确性、质量标准、检查步骤或异常处理。

## 5. 内容验收方法只写在 procedure

交付件内容是否正确、质量是否达标，其检查方法、判定依据和不合格处理全部写在 `procedure`，由验收者独立执行。`acceptance` 与 `procedure` 不得描述同一项检查。

## 6. 执行产生证据，验收独立审查，不重复执行

`approach` 描述执行者如何产出交付件。功能验证、性能测试和环境探测本身可以是执行任务：执行者实际运行这些工作，交付代码、原始记录及结果报告，但不替验收者裁决自己的交付件是否满足要求。不要按“检查”“验证”等词机械划分字段，应区分实际执行与验收裁决。

`procedure` 描述验收者如何独立审查交付件及证据。独立验收不等于重复运行：尤其对耗时的性能用例，不要求 developer 和 verifier 各跑一遍。verifier 检查测试代码、执行记录和报告的真实性、完整性、相互一致性及与当前实现版本的对应关系，再按任务标准给出结论，不能只接受执行者的“通过”自述。

### 执行证据与复用边界

- 执行者交付完整的测试或性能用例代码、运行命令与参数、环境信息、实现及用例版本、退出码、逐例原始结果和汇总报告。证据按任务所需记录，每次执行的原始资料保留一份，报告引用其路径，不重复抄录。
- 验收者检查用例是否实际测量了目标行为、是否覆盖约定范围，报告能否追溯到原始结果，是否存在跳过、缺失、版本不符、相互矛盾或疑似伪造的证据。根据原始结果核对指标与判定依据，不重复跑同一批构建、测试或性能测量。
- 证据足够支撑判定时直接验收；证据不足、可信性无法确认或结果不满足要求时不通过，指出需要补充或修复的具体内容，交回执行节点处理。verifier 不通过自己重跑来替执行者补交付件。
- 补充证据不等于全量重跑。仍有效的代码和记录继续复用；只有相关实现、输入、用例或环境变化使原证据失效，或者必要证据缺失时，才由执行者完成所需范围的重新执行。

两者职责是“执行并提供可审查证据”与“审查证据并独立裁决”。无需重复执行不能成为降低证据要求的理由；未真实执行的工作不得写成已验证。

## 边界对照示例

| 字段 | 错误写法 | 正确写法 |
|---|---|---|
| `goal` | 生成 `$WORK_DIR/spec.yaml` 并通过 12 项校验 | 将已确认需求转换为结构化算子规格 |
| `approach` | 执行性能用例后自行认定已通过验收 | 执行性能用例，保存代码、参数、版本、逐例原始结果和报告 |
| `acceptance` | `spec.yaml` 覆盖全部接口、无 TODO、校验返回 0 | `test -s "$WORK_DIR/spec.yaml"` |
| `procedure` | 把 developer 已执行的整批性能用例再跑一遍 | 审查用例代码及执行证据，核对真实性、完整性、版本对应关系和性能指标；不足时退回补齐 |

## 维护检查

修改 task 提示词或组装逻辑时，分别从执行者和验收者实际可见的字段检查约定是否完整，再逐项核对上述六条规则。重点检查是否重复验收上游、把内容质量要求放进 `acceptance`、把验收动作放进 `approach`，或将本节点问题后移。

组装后的节点仍须保留字段语义与可见性边界，不能通过合并提示词把 `approach` 和 `procedure` 同时下发给双方。

补充 Skill 的提示文本与挂载名单在同一结构化声明中维护，文本点名的能力须列入对应阶段的 `skills` 或 `skills_by_platform`；不从自然语言猜测绑定。固定项与补充项共同构成阶段能力集合，候选项挂载不代表无条件加载；保留原触发条件与平台范围，并从实际阶段工作区验证可访问性。
