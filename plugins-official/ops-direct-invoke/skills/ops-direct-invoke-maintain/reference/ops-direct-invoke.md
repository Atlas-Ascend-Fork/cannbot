# ops-direct-invoke Skill 的设计思想

## 为什么需要独立的算子流程入口

PM 承接的工作不局限于完整算子开发，因此通用 PM 指引不应内置算子的全部流程。将算子开发规则集中在 `ops-direct-invoke` Skill，使 PM 在收到相应需求时才加载这些约束，也让流程演进不影响其他任务。

入口负责指导 PM 将需求组织为可执行工作流，不代替子 Agent 完成任务，也不承担调度器的职责。

## 为什么把任务内容与合作关系分开

`tasks/` 表达单个节点要完成什么、如何产出和验收；`workflows/` 表达节点之间如何合作。一个任务可以被不同流程复用，同一流程也可以调整依赖和预算，而不必复制、改写整段任务提示词。

维护时将节点的业务契约放在 task，将本轮合作关系放在 workflow。不要把某一张图中的顺序、节点编号或重试预算当成任务本身不可改变的属性。具体字段归属应遵循组装接口，但接口实现不应被当成永久设计限制。

Skill 提供知识和方法，task 显式声明本节点所需能力。这样角色身份可以保持稳定，父仓的通用流程也能通过子仓的同名 Skill 适配不同工程环境。

## 为什么在下发前组装完整 YAML

可复用模板适合维护，完整任务定义适合执行。组装层负责把 task 引用、本轮参数和产物引用转成明确输入，让 harness 接收到自包含的节点定义，不需要理解业务模板体系。

组装是确定性的转换，不替 PM 选择业务路线，也不根据模糊任务名称推断能力。错误输入应在下发前被发现，不能留下看似可执行的半成品。

共享模板与单轮执行文件分开，使未来的模板修改不会改变已经启动或需要恢复的工作流。每轮启动前准备本轮完整 YAML，可根据已完成任务、有效产物和剩余目标重新编排；复用产物不要求复用原任务图。新一轮使用独立目录并保留前轮记录，恢复中断的同一轮则沿用原 YAML 与输入，不重新组装或覆盖。

## 为什么围绕 harness 组织，而不再写一套调度器

本工作流负责“下发什么”，harness 负责“如何执行调度”。启动包装层只处理必要的参数和进程接口，不自行实现派发、重试、回滚、裁决或状态推进。

这使业务流程可以演进，而无需维护两套互相竞争的状态机。维护时把 harness 当作可信依赖，通过公开接口使用它；回归测试检查我们是否改坏了输入和调用衔接，不重新证明框架内部机制正确。

任务的环境选择必须落实到实际子进程，不能只出现在提示词中。启动包装层可以加载已确认的激活脚本并传递工作目录；它不安装依赖、不替用户选环境，也不把开发解释器与运行 harness 所需的解释器混为一谈。恢复保持相同激活约定并保留历史日志。

报告用于保存业务事实和证据，不能代替框架裁决，也不能通过修改报告或内部状态强行推进流程。

## 为什么执行必须有界、可观测且可恢复

自动执行的价值在于减少人工盯守，不能以无限重试换取表面上的自主性。可能循环的节点和多轮修复应有明确预算或停止条件；不能在预算耗尽后无条件新开一轮规避上限。无法继续时保留失败证据、阻塞点和已完成交付，向用户说明需要的决策。

进度和恢复依据必须落在外部可追溯记录中，不能只存在于 PM 的上下文。调度状态与恢复使用 harness 的公开能力，业务事实由任务报告承载，不另建竞争的状态机。恢复复用已通过且仍有效的产物；仅对变化影响或证据失效的范围重新执行。

先处理可预见的依赖与输入访问缺口，将获准的准备工作及其依赖关系落到本轮任务中，避免进入开发后才发现必要环境或权限缺失。交付需要时仍可组织多轮；独立运行记录不要求重新克隆只读资产或重复确认任务授权。harness 及其调度 Skill 保持黑盒契约，不通过修改公共基础设施或角色身份来实现业务流程策略。

PM 通过框架状态了解执行进度，按需读取阻塞证据，不在运行期间反复通读产物。这样既保持可观测性，也避免把静默执行变成持续消耗上下文的人工监工。

## 为什么扩展必须有契约并保持基线独立

附加流程应自带明确的输入、输出、完成条件、失败处理和有界执行约定，使扩展可以作为清晰的任务单元理解与复用。执行和验收仍须分离，不能因为是扩展就放宽交付要求。

通用流程依赖扩展点的契约，不依赖某个具体扩展的内部实现；未启用扩展时，基线仍应独立完成其承诺的交付。启用扩展时明确接入位置、依赖和写入范围，出现顺序或资源冲突先解决歧义，不依靠隐含执行顺序。扩展输出必须满足后续任务的输入契约。

这些原则用于指导能力扩展，不要求建立独立的插件注册、固定阶段挂载或额外调度机制；具体组合仍由 workflow 表达并交给 harness 执行。

## 为什么支持动态实现子图

算子实现应按实际设计拆分，而不是预设固定数量的开发节点。只有形成设计、实现单元和验证义务后，才有足够信息组织具体实现任务。

动态子图把这些业务产物转换为同一 harness 能执行的节点图，既保留按任务拆分的灵活性，又不引入另一套执行循环。依赖应反映能力前提；并行任务的写入范围应避免冲突，无法确认独立性时不盲目并行。

运行期生成子图应是主图明确声明的任务产物，不意味着 PM 可以随意改写已启动的流程。子图定义、业务报告和框架状态即使位于相邻目录，也应保持各自的写入边界。

## 为什么将设计汇总和文档模板独立出来

分文件设计便于按主题维护，部分消费者需要完整设计输入；汇总层解决表示形式差异，不应重新设计、补造事实或形成另一份独立维护的设计。

文档模板统一交付格式，使证据容易被消费和验收。模板不负责调度，也不自行定义新的交付范围；由 task 明确产出者、路径和验收方法。避免在模板、task 与入口重复维护同一规则。

## 维护约束

修改时先判断影响的是知识、节点契约、合作关系、组装接口还是启动接口，再修改对应层。接口变化同时检查生产方与消费方，不靠下游猜测新格式。

修改 task 的内容组织与验收边界时，阅读 [Task 组织规范](task-authoring.md)。具体可用模板、脚本名称、参数和目录清单由对应 Skill、使用文档及实际实现说明，不在这里固定。
