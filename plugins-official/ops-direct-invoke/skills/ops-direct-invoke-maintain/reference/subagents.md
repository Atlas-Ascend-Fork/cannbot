# 子 Agent：身份层

## 模块范围

插件 `agents/` 下的三个角色定义，以及安装器为不同客户端生成的对应角色配置。角色职责与 `ops-direct-invoke` Skill 中的介绍保持一致。

## 设计思想

子 Agent 只承担身份层：定义“我是谁、负责哪类工作、有哪些权限边界”。领域知识和工作方法由 Skill 提供，当前任务的输入、输出和验收要求由 task 声明。

| Agent | 职责 | 典型交付件 |
|---|---|---|
| `ops-direct-invoke-architect` | 负责所有规划、探索类工作 | 设计文档或探索报告 |
| `ops-direct-invoke-developer` | 负责代码开发、功能验证等需要具体执行的工作 | 具体代码或执行结果 |
| `ops-direct-invoke-verifier` | 负责所有验收类工作 | 通过或不通过的结论，可附被验收内容的修改意见 |

这些角色按工作性质划分，不按某个算子、开发语言、仓库或固定流程阶段划分。同一身份可承担不同业务任务，所需知识随 task 选择的 Skill 变化。

### 身份与知识分离

- 角色文件不绑定具体 Skill，不维护必读 Skill 清单，也不嵌入领域知识、仓库规范或具体操作教程。
- PM 或 task 根据实际任务显式组合 Skill；执行者使用的能力写在执行提示词中，验收者使用的能力写在验收提示词中，遵循 task 的字段可见性边界。
- 修改知识或工作方法时维护对应 Skill；修改角色的职责、权限和通用行为边界时才维护角色文件。

角色层不负责流程编排或派发其他 Agent。PM 组织任务，harness 负责实际调度；子 Agent 在当前任务及角色边界内工作。

### 执行与验收的分工

developer 负责实际功能验证、性能测量等执行工作并交付完整证据；verifier 负责独立审查和裁决，不重复运行同一批用例，也不以执行者自述代替证据。证据不足时指出缺口并退回执行节点处理。具体 task 的证据与复用约定见 [Task 组织规范](task-authoring.md#6-执行产生证据验收独立审查不重复执行)。

### 为什么执行与验收必须是不同实例

同一个实例容易沿用自己的实现假设，把自检结论当成验收依据。执行者与验收者应由不同 Agent 实例承担，验收职责由 verifier 承担；只切换称呼或要求执行者再读一遍产物不能形成独立验收。实例隔离由 harness 调度实现，工作流使用该能力，不另行看护框架内部机制。

独立实例通过交付契约和证据协作，无需了解对方的内部思考或完整上下文。独立性要求的是独立判断，不要求重复执行昂贵的测试。

## 维护方法

1. 修改角色时，对照 `ops-direct-invoke` Skill 核对三类职责与典型交付件，避免出现两套不同的角色定义。
2. 检查新增内容是否属于身份层：通用职责和权限可以保留；具体 Skill 名称绑定、领域规则及操作步骤应放回 task 或 Skill，不随角色常驻加载。
3. 不因新增工作阶段就新增角色或将现有角色固定在该阶段；按规划探索、具体执行、验收的工作性质选择已有身份。
4. 角色名称是 task 与客户端配置之间的引用契约。修改名称时同步核对 task、workflow、动态子图生成器和安装声明，确保实际客户端能加载对应角色。
5. 修改角色源文件后，核对安装生成的配置是否同步。客户端格式可以不同，但身份、职责和权限语义应一致；遵循入口中的安装副本维护要求。
