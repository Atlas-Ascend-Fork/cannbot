# AGENTS.md：PM 入口

## 工作区 Agent 的入口

在工作区中启动 harness 工具时，最外层 Agent 加载 `AGENTS.md`，按照其中的约定承担 PM 职责：与用户对齐需求、规划任务、组织子 Agent 协作并汇总交付。

`AGENTS.md` 保持为薄层入口，描述 PM 的通用工作方式；算子开发的具体流程由 `ops-direct-invoke` Skill 承担，不在入口重复维护。

## 为什么先对齐需求，再静默执行

用户应在需求对齐开始时知道还需参与问卷，并在对齐结束后明确知道可以离开。这样既避免实现阶段反复追问，也不把缺失需求变成未经确认的承诺。

发问前先集中梳理需求、执行环境选择与修改权限，尽量同批问齐；题数限制导致的分批应连续进行，真正依赖前一答复的问题才分阶段。解释器与工具链选择属于用户约定，内部目录和启动参数属于 PM 的实现细节；不能漏问前者又反复要求批准后者。

静默执行减少非必要交互和进度噪声，不改变权限、验收、重试预算和恢复边界。已确认范围内由 PM 自主推进；遇到无法在授权范围内解决的阻塞时，保留状态并集中说明需要的决定。用户没有回复不能自动视为接受需求变更或授权越界。

需求与权限确认绑定整个任务的目标与授权边界，不绑定单轮目录或 prompt 字符串；调度接口要求的具体输入确认仍按其契约处理。恢复、重试及新轮继承有效任务约定，只有实质变更才补充需求或授权。多轮 Workflow 是正常的交付组织方式；减少失败重开依靠启动前补齐输入、环境与权限缺口，不以限制轮数代替排错。

## 为什么入口定制不能改变 PM 身份

子仓可以补充本仓约束，但入口仍需保留需求对齐、任务分流、必须加载的能力和统一调度边界。否则同一工作流会随安装位置改变基本职责，子 Agent 和 Skill 的契约也会失去稳定前提。入口不承载仓库知识正文，也不通过定制让 PM 接管工程执行。

## 维护方法

修改 PM 指引时保留通用任务与算子开发的分流，只将通用职责、需求对齐、任务规划、执行与交付约定放在入口中。具体算子流程与能力绑定留在对应 Skill 和 task 中。

不同客户端可能使用 `AGENTS.md` 或 `CLAUDE.md` 承载项目指引，以上设计同样适用。更新安装后的指引时保留插件管理区块之外的用户内容；涉及源文件与安装副本同步时，遵循 [入口中的通用维护要求](../SKILL.md#通用维护要求)。
