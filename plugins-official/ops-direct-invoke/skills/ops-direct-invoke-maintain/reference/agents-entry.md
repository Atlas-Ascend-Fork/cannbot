# 按需加载的 PM 入口

## 主会话职责与节点分工

`ops-direct-invoke` Skill 是主会话承接用户算子任务的 PM 入口，接收原始需求并负责对齐、编排和交付。PM 职责按任务加载，只在承接完整任务的主会话中生效。

子 Agent 的身份与权限由客户端角色配置定义，当前工作由 harness 派发的 task 指定。PM 组织协作，节点负责执行与验收，harness 负责调度，使完整任务与单个节点各自具有明确的职责范围。

入口元数据标明主会话算子任务这一适用范围，正文说明职责边界。节点使用角色、task 和下发的知识能力，按需读取模板、脚本或参考资料，保持自身角色与权限。

## 为什么先对齐需求，再静默执行

用户应在需求对齐开始时知道还需参与问卷，并在对齐结束后明确知道可以离开。这样既避免实现阶段反复追问，也不把缺失需求变成未经确认的承诺。

发问前先集中梳理需求、执行环境选择与修改权限，尽量同批问齐；题数限制导致的分批应连续进行，真正依赖前一答复的问题才分阶段。解释器与工具链选择属于用户约定，内部目录和启动参数属于 PM 的实现细节；不能漏问前者又反复要求批准后者。

静默执行减少非必要交互和进度噪声，不改变权限、验收、重试预算和恢复边界。已确认范围内由 PM 自主推进；遇到无法在授权范围内解决的阻塞时，保留状态并集中说明需要的决定。用户没有回复不能自动视为接受需求变更或授权越界。

需求与权限确认绑定整个任务的目标与授权边界，不绑定单轮目录或 prompt 字符串。调度 Skill 的四项启动输入由 PM 根据已确认任务和当前客户端代答，无法确定的项才在初始问卷询问；代答不扩展授权或取代节点审批。恢复、重试及新轮继承有效任务约定，只有实质变更才补充需求或授权。多轮 Workflow 是正常的交付组织方式；减少失败重开依靠启动前补齐输入、环境与权限缺口，不以限制轮数代替排错。

## 安装与会话生效

安装器将 PM Skill 与子 Agent 角色安装到对应客户端目录，并维护来源和路径记录。项目 `AGENTS.md` / `CLAUDE.md` 中若存在本插件的完整管理区块，安装时清理该区块，保留区块之外的用户文字和其他插件指引。

安装与重复更新保持幂等；没有完整管理标记的内容由用户确认和维护。更新后开启新会话，以加载当前配置。

## 维护方法

修改 PM 入口时核对原始需求、首次集中确认、工作区定位、权限、每轮编排与交付职责是否完整。具体节点能力与交付契约由 task 声明，仓库知识由对应 Skill 提供，工程执行由子 Agent 完成。

检查安装、文档、测试及维护资料中的入口与职责描述是否一致；安装回归验证配置同步、管理区块清理与用户内容保留，真实客户端验证主会话和节点身份加载。涉及源文件与安装副本同步时，遵循 [入口中的通用维护要求](../SKILL.md#通用维护要求)。
