## What I do

Take `output/{op_name}/{op_name}_dsl.py` (an easyasc DSL file) and turn it into a `custom_opp_ubuntu_aarch64.run` installer at the path `ascendc-evaluation` already knows how to consume. I do this in three steps:

1. Run easyasc's `OpExec(simulator=False, gen_only=True, out_dir=...)` to emit AscendC `.cpp/.h` files into a self-contained, isolated project directory `output/{op_name}/easyasc_workspace/{op_name}_raw/`.
2. Run that project's own `build.sh` (with `${ASCEND_HOME_PATH}` sourced) to produce `output/{op_name}/easyasc_workspace/{op_name}_raw/build_out/custom_opp_*.run` AND the autogenerated aclnn header at `.../build_out/autogen/aclnn_*.h` (used by the next stage as ground truth for parameter ordering).
3. Soft-link the `.run` into `output/{op_name}/{op_name}Custom/build_out/custom_opp_*.run` so downstream `ascendc-evaluation` finds it at the same path it always has. The `{op_name}Custom/build_out/` directory is created here (this responsibility moved from `easyasc-dsl-bridge` in v2.1 — bridge now runs AFTER codegen).

This skill does NOT install the `.run` and does NOT run on device — that's `ascendc-evaluation`'s job.

> **v2.1 changelog**: easyasc codegen output is now under `easyasc_workspace/{op_name}_raw/` (mirrors fm-easyasc's `_raw` isolation). The previous flat layout (`output/{op_name}/{op_name}_easyasc/`) had two problems: (a) cake's generic `cake-code-review` skill defaults to looking at `{Op}Custom/op_kernel/` but the real source was elsewhere, creating an implicit jump; (b) it left no room to keep a "last known good" snapshot separate from the working tree. The new layout fixes both.

## Sub-Agent Strategy

Side-effects (filesystem writes, build logs, possible failures) are best contained in a sub-agent so the orchestrator context stays clean.

**When called from cake**: delegate to a `general-purpose` sub-agent with this SKILL.md content + the values of `${EASYASC_DSL_HOME}`, `${ASCEND_HOME_PATH}`, and the target `op_name`.

**When called directly**: run the workflow inline.

## Prerequisites

- `${EASYASC_DSL_HOME}` is set and points at a populated `ops-easyasc-dsl` (cake stage 0 enforces this and runs `init.sh` if needed).
- `${EASYASC_DSL_HOME}/easyasc/` is on `PYTHONPATH`. cake stage 0 sets `PYTHONPATH="${EASYASC_DSL_HOME}:${PYTHONPATH}"`. If running this skill standalone, do the same first.
- `${ASCEND_HOME_PATH}` is set and `${ASCEND_HOME_PATH}/bin/setenv.bash` exists (CANN install).
- `output/{op_name}/{op_name}_dsl.py` exists and was simulator-verified by `dsl-baseline-generation-easyasc`.
- `output/{op_name}/{op_name}_op_desc.json` exists — the script reads input shapes/dtypes from it.

> **No longer required** (v2.1): `{op_name}Custom/build_out/` no longer needs to pre-exist — this skill creates it. (In v2.0 the bridge ran before codegen and created the empty dir as a soft-link target placeholder; v2.1 reverses the order.)

## a2 / a5 hardware gate

This skill produces real AscendC only for **a2** (ascend910b). The target is
read from `output/{op_name}/easyasc_workspace/codegen_status.json` →
`target_device` (seeded by `scripts/init_workspace.sh` at cake stage 0; the
agent picks a2/a5 from host device detection or an explicit
`operator_type: easyasc-a5` in op_desc.json):

- **a2** — run the full Step 1–3 workflow below (codegen → build → softlink).
- **a5** — **simulator-only, terminal**. The validation gate is
  `scripts/run_smoke.py`, which runs the DSL file's `__main__` self-check
  (`OpExec(simulator=True)` vs a torch reference — easyasc's simulator runs on
  any host, no a5 NPU needed) and records `smoke.passed` + sets
  `next_step="report-only"` (pass) or `"human-intervention"` (≥3 fails). a5
  does **not** run real codegen: `run_codegen.py` refuses it (exit 2). No `.run`
  / aclnn header is produced, so the bridge (stage 6) and `ascendc-evaluation`
  (stage 8) are **skipped** — the agent jumps to cake-review (report-only).

a5 smoke command:
```bash
PYTHONPATH="${EASYASC_DSL_HOME}:${PYTHONPATH}" \
  python3 ${CLAUDE_SKILL_DIR}/scripts/run_smoke.py {op_name} --output-root output
```

If `codegen_status.json` is absent, the codegen driver defaults to a2 (backward
compatible). Device detection helper: `scripts/check_device.sh --target {a2|a5}`
(parses `npu-smi info`: `910B`→a2; non-910B→a5/simulator-only). On a2,
`run_smoke.py` may be used as an advisory pre-check, but a2 may fall through to
codegen even on smoke failure (accuracy/perf deferred to the AscendC layer).

## Workflow

### Step 1 — verify the DSL kernel name
The kernel function in `{op_name}_dsl.py` MUST be `def {op_name}_custom(...)`. If the name is different, the codegen output will register a mismatched op_type and `ascendc-evaluation` will fail to load it. Verify by grepping:

```bash
grep -E "^@kernel\(\)|^def {op_name}_custom\(" output/{op_name}/{op_name}_dsl.py
```

If the kernel function has a different name, return control to `dsl-baseline-generation-easyasc` with a fix request — do NOT silently rename.

### Step 2 — run codegen + build + softlink (single command)
Invoke the helper driver with `--build`:

```bash
cd <repo root>   # the directory containing the `output/` tree
PYTHONPATH="${EASYASC_DSL_HOME}:${PYTHONPATH}" \
  python3 ${CLAUDE_SKILL_DIR}/scripts/run_codegen.py {op_name} --build
```

`run_codegen.py --build` does the whole pipeline in one shot:

1. Reads `output/{op_name}/{op_name}_op_desc.json` to discover input/output shapes & dtypes.
2. Imports `output/{op_name}/{op_name}_dsl.py` and locates the `{op_name}_custom` kernel via `getattr`.
3. Calls `OpExec(kernel, simulator=False, gen_only=True, out_dir="output/{op_name}/easyasc_workspace/{op_name}_raw")(*build_codegen_inputs())`.
4. Patches the emitted `build.sh` (pre-creates `binary/config/` so CPack doesn't crash on partial rebuilds) and renames any PascalCase kernel files in `op_kernel/` to snake_case (the AscendC compile harness expects snake_case).
5. Sources `${ASCEND_HOME_PATH}/bin/setenv.bash` and runs `bash build.sh` inside the workspace → produces `easyasc_workspace/{op_name}_raw/build_out/custom_opp_*.run` and `easyasc_workspace/{op_name}_raw/build_out/autogen/aclnn_*.h`.
6. Creates `output/{op_name}/{op_name}Custom/build_out/` and softlinks the `.run` into it.

> Why not run easyasc's top-level `b.sh`? Because that wrapper also runs `bash <run> --install-path=...` which would install the custom op into `${EASYASC_DSL_HOME}` rather than where `ascendc-evaluation` wants it. We only want the `.run` artifact; CAKE evaluation handles install at its own path.

If codegen / build fails:
- **Codegen errors** (kernel signature mismatch, unknown A2 API, etc.) — fix the DSL and re-run. `OpExec(gen_only=True)` is fast (<10s for vector ops).
- **Build errors** (compile failures from `build.sh`) — follow `ascendc-op-debug`. Build errors that point at easyasc-emitted source (`tensorutils.h`, cube/vec headers) are usually a DSL bug, not a CANN bug — go back to stage 4.

### Step 3 — verify the next stage can find what it needs

The bridge (cake stage 6) needs the aclnn header at a deterministic path. Quickly check:

```bash
ls output/{op_name}/easyasc_workspace/{op_name}_raw/build_out/autogen/aclnn_*.h
ls -l output/{op_name}/{op_name}Custom/build_out/custom_opp_*.run    # should be a symlink
```

If either is missing, the build did not complete successfully — re-run `run_codegen.py --build` after fixing the underlying issue. Do NOT proceed to the bridge stage with a broken codegen output.

### (Standalone use only) — run codegen without building
For dev workflows where you want to inspect the emitted AscendC sources without paying for a full build, omit `--build`:

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/run_codegen.py {op_name}
# Then manually:
( source "${ASCEND_HOME_PATH}/bin/setenv.bash"
  cd "output/{op_name}/easyasc_workspace/{op_name}_raw"
  bash build.sh )
```

In this mode the script does NOT softlink the `.run` — you'll need to do that yourself if you intend to evaluate. The cake workflow always uses `--build`.

## Output files

- `output/{op_name}/easyasc_workspace/{op_name}_raw/`  — full easyasc-generated AscendC project (isolated `_raw` namespace)
  - `op_kernel/{snake}_custom.cpp` (+ `_cube.h`, `_vec.h`, `tensorutils.h` if applicable)
  - `op_host/{op_name}_custom.cpp` + `_tiling.h`
  - `CMakeLists.txt`, `CMakePresets.json`, `build.sh` (CPack-robustness patched)
  - `build_out/custom_opp_*.run`
  - `build_out/autogen/aclnn_{snake}_custom.h` ← **bridge (stage 6) reads this as ground truth**
- `output/{op_name}/{op_name}Custom/build_out/custom_opp_*.run` (symlink → above)

## Notes

- Do NOT delete or rewrite the easyasc-generated `.cpp/.h` files — they are the source of truth for this op. If a fix is needed, edit `{op_name}_dsl.py` and re-run this skill; codegen will regenerate the `.cpp/.h`.
- Do NOT manually copy the `.run` instead of symlinking. A symlink keeps `output/{op_name}/easyasc_workspace/{op_name}_raw/build_out/` as the canonical location and avoids drift if the build is re-run.
- The `_aclnn_test/` directory that `OpExec(simulator=False)` would normally generate is **not** produced when `gen_only=True` — that's intentional. CAKE's own `test_cases.py` is what evaluation runs against.
- The aclnn header at `easyasc_workspace/{op_name}_raw/build_out/autogen/aclnn_*.h` is the single source of truth for the next stage (bridge) — do not move, rename, or hand-edit it.

## Regression test

`scripts/regression_test.py` runs the full cake downstream pipeline
end-to-end and verifies every P0/P1/P2 fix point is still working. Use it
to catch regressions when modifying any of the related skill scripts.

```bash
# Fast (skip eval, ~2 min): verifies build pipeline + skill-fix signals
python3 skills/easyasc-codegen/scripts/regression_test.py AddRMSNorm --skip-eval

# Full (~25 min): also runs evaluate.py and checks pass count ≥ threshold
python3 skills/easyasc-codegen/scripts/regression_test.py AddRMSNorm
```

The test checks these fix-point signals automatically:

- **P0-1 / P0-3** ``aclnn{Camel}Custom`` name preserves internal capitals
- **P0-2** kernel cpp files renamed PascalCase → snake_case after codegen
- **P1-1** `build.sh` patched to pre-create `binary/config/` for CPack robustness
- **P1-2** bridge cpp emits bf16↔fp32 cast layer when DSL/op_desc dtypes differ
- **Build** `.run` builds in one shot from clean state, no manual patches
- **Eval** (full mode only) ``passed_cases >= EXPECTED_PASS_MIN[op_name]`` (default 11/12 for AddRMSNorm)

Exit codes: 0 = all OK, 1 = stage failure, 2 = below pass threshold, 3 = skill regression.
