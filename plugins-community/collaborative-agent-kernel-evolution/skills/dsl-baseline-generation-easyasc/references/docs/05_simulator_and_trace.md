# Simulator and Trace

The simulator is still the safest first execution target in this repository, but the implementation path has changed significantly.
The active runtime is now the V2 simulator under `easyasc/simulator_v2/`.

## 1. What the simulator covers now

The current simulator stack covers:

- program building from emitted kernel instructions
- control-flow-aware lane programs
- parent/child runtime orchestration across simulated cores
- cube, vec, and micro execution inside the V2 runtime
- intra-core and collective synchronization
- shared-tensor / workspace storage
- optional Chrome/Perfetto-style trace export

This makes simulator mode the default choice for:

- first-pass validation
- synchronization debugging
- reproducing parser/runtime behavior in tests

## 2. How to run in simulator mode

Use:

```python
out = OpExec(kernel_fn, simulator=True)(...)
```

Accepted spellings:

```python
out = OpExec(kernel_fn, simulator=True)(...)
out = OpExec(kernel_fn, simulator="v2")(...)
out = OpExec(kernel_fn, simulator="legacy")(...)
```

Important current behavior:

- all three forms above enable the current simulator runtime
- `OpExec` normalizes the `simulator` argument to a boolean flag
- `KernelBase.run_sim()` always dispatches to `_run_sim_v2()`
- `simulator="legacy"` is kept only as a compatibility spelling; it does **not** select a separate old runtime anymore

In simulator mode:

- input PyTorch tensors are cloned into `GMTensor.data`
- the kernel builds a V2 `KernelProgram`
- the V2 runtime copies the bound tensors into its shared tensor store
- outputs are copied back from the runtime tensor store into `GMTensor.data`, then returned to PyTorch

## 3. How a kernel becomes a V2 program

Program building happens in `easyasc/kernelbase/kernelbase.py`.

The selection order is:

1. `kernel._simulator_v2_program_builder`
2. `kernel._simulator_v2_program`
3. automatic bridge selection

Automatic bridge selection works like this:

- if the instruction stream contains loops, conditionals, topology queries, `call_micro`, `VarList`, or cross-lane sync helpers, V2 uses `easyasc/simulator_v2/compat/control_flow_bridge.py`
- otherwise V2 uses the narrower linear bridge in `easyasc/simulator_v2/compat/kernel_bridge.py`

That means the runtime is no longer just “execute lowered instructions directly”.
There is now a real bridge layer between emitted instructions and the executable simulator program.

## 4. Runtime shape

The V2 runtime is layered:

- parent coordinator: `easyasc/simulator_v2/runtime/global_runtime.py`
- per-core child process wrapper: `easyasc/simulator_v2/runtime/core_process.py`
- per-core runtime: `easyasc/simulator_v2/runtime/core_runtime.py`
- lane-level control interpreter: `easyasc/simulator_v2/runtime/control_actor.py`
- per-pipe worker threads: `easyasc/simulator_v2/runtime/pipe_worker.py`
- pipe executors: `easyasc/simulator_v2/ops/`

Practical mental model:

- one parent runtime prepares shared tensors and the execution plan
- one child process is launched per simulated core
- inside each active core, each active lane gets a `ControlActor`
- each logical pipe inside that lane is served by a threaded `PipeWorker`

## 5. Core count, lane activation, and memory

Three files matter most here:

- `easyasc/simulator_v2/config.py`
- `easyasc/simulator_v2/runtime/execution_plan.py`
- `easyasc/simulator_v2/memory/`

Current behavior:

- default core count follows the active device family (`950 -> 32`, `b3 -> 20`)
- V2 can skip inactive lanes when a program only uses a subset of cube/vec lanes
- runtime tensor and workspace storage are prepared up front through the shared tensor store
- mixed-lane kernels rely on metadata generated by the bridge, especially for lane-local UB handling

Scalar reminder:

- control-flow kernels preserve scalar `Var` expressions such as `var_add`, `var_mul`, and `var_div` into the runtime
- on the V2 path, these scalar ops must preserve float semantics when the DSL `Var` is float
- if a kernel's raw `L0C -> UB` data looks correct but a later `@vf()` scale suddenly becomes all zero, inspect float `Var` arithmetic in `control_actor.py` and `ops/micro/runtime.py` before blaming the cube/vec handoff

## 6. Why simulator-first is still the repository norm

Most runnable kernel files in `agent/example/kernels/` still validate themselves with:

```python
OpExec(..., simulator=True)
```

The reasons remain the same:

- faster iteration on kernel logic
- easy comparison against inline PyTorch references
- direct access to synchronization and trace behavior
- fewer moving pieces than generation/runtime debugging

## 7. Generating a trace

Trace export is only supported in simulator mode.

Example:

```python
trace_path = os.path.join(out_dir, "trace.json")
out = OpExec(kernel_fn, out_dir, simulator=True, trace=trace_path)(...)
```

Current trace flow:

- each simulated core records its own events
- the parent runtime merges per-core traces after execution
- the merged result is exported as Chrome/Perfetto-style JSON

Useful reference tests:

- `testcases/simulator/trace/test_trace.py`
- `testcases/simulator/trace/test_simulator_v2_trace.py`
- `testcases/simulator/opexec/test_opexec_simulator_v2_kernel_bridge.py`

## 8. What the trace is good for

Use the trace when you need to answer questions like:

- which lane or pipe ran first
- whether a producer/consumer handoff happened in the order you expected
- whether waits, events, or barriers are stalling progress
- whether the actual pipeline shape matches your intended topology

The trace is especially useful for:

- `auto_sync()`
- cross-side mutexes
- mixed cube/vec kernels
- one-tile lookahead or delayed-consumer flows

## 9. Suggested debugging loop

When a kernel does not work:

1. reduce the shape
2. run in simulator mode
3. compare against a direct PyTorch reference
4. if synchronization is involved, enable tracing
5. inspect the bridge/runtime path before patching the kernel blindly
6. only after simulator parity, try generation or hardware-facing flow
