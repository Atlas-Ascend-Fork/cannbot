## Reading Path

1. Read `{op_name}_functional.py` + `op_desc.json` → understand inputs, compute, access pattern
   - Field-by-field contract, accepted values, and a copyable template → `references/input_contract.md`
   - Invoking this skill standalone (no upstream stage)? Author both files from that contract first.
2. Answer Q1–Q6 (§ Model Selection below) → select Model A, B, or C
3. Read `references/pass_details_model_{A|B|C}.md` → follow passes sequentially
   - Each file is self-contained — do NOT read other model files
   - Compilable skeleton is at the top — copy it, fill in the compute body
   - Multi-dtype dispatch is included in the skeleton
   - For msopgen projects → also read `references/msopgen_adaptation.md` (tiling data, host function, CMake)
     - Fill the whole tiling contract (every kernel-read field) → Step 2b
     - If `op_desc.json` declares an **array/ListInt** attribute (`perm`, `axes`, `dims`) → Step 2c (OpDef `.ListInt()`, permuting InferShape, inline-array tiling, `__gm__`-global VF plumbing, `pytorch_npu_helper.hpp` wrapper). Do NOT stub it.
4. Write the compute body from operator semantics
   - Consult `references/simt_operator_patterns.md` to identify which pattern your operator matches
   - If stuck → consult `references/operator_examples/` for a similar access pattern
   - If your compute body needs warp ops → read `references/simt_warp_ops.md`
   - If it needs cache hints or UB staging → read `references/memory_optimization_guide.md`
   - If it needs atomics/CAS/compaction → read `references/simt_advanced_patterns.md`
   - If op_desc.json lists multiple dtypes → read `references/simt_multi_dtype_guide.md`
5. Before finalizing → check error corrections table (§ Error Corrections below)
   - Compile flags, the four include paths, and the compiler-error table → `references/simt_build_and_compile.md`

> **Standalone vs msopgen — decide this before writing a line of code.**
> A kernel written for an msopgen project uses `GET_TILING_DATA`, which is
> **generated by the project's build system and does not exist in the CANN
> headers**. A standalone `.asc` carries its own `main()` and reads tiling from
> plain arguments instead. Do not mix the two forms.
> To type-check a project kernel outside its build, put the `#ifndef GET_TILING_DATA`
> fallback in its tiling header — `references/get_tiling_data_pattern.md`.
> See also `references/simt_build_and_compile.md`.


## Prerequisites

SIMT operators require `ascend950` as the compute unit. When Stage 6 (ascend-call-generation) generates the msopgen project, it **must** pass `--soc ascend950` to `gen_project.py` so that CMakePresets.json and op_host are generated with the correct SoC target. Without this, the default `ascend910b` is used and compilation will fail or produce wrong artifacts.

### Build commands

Copy-paste recipes live in **`references/simt_build_and_compile.md`** Quick Reference; the reasoning behind
each flag is in **`references/simt_build_and_compile.md`**. Read one of them before
the first compile — every flag was learned from a failed build. The recipes in brief:

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
A="$ASCEND_HOME_PATH/$(uname -m)-linux"

# Standalone .asc (has its own main(); no GET_TILING_DATA)
bisheng --asc-aicore-lang --npu-arch=dav-3510 -std=c++17 -O2 MyOp.asc -o myop \
  -I"$A/include" -I"$A/asc/include" -I"$A/asc/impl" -I. \
  -L"$A/lib64" -Wl,-rpath,"$A/lib64" -lascendcl -lruntime -lm

# msopgen project kernel (syntax check only; both flags are required)
bisheng --asc-aicore-lang --npu-arch=dav-3510 --cce-aicore-only \
  -std=c++17 -O2 -D__NPU_TILING__ \
  -c my_op_custom.cpp -o my_op.o \
  -I"$A/include" -I"$A/asc/include" -I"$A/asc/impl" -I.

nm -C my_op.o | grep -c 'simt_'   # must be > 0 — see below
```

Six things that are easy to get wrong:
- **`--cce-aicore-only` is mandatory on a `-c` compile, and it fails silently.**
  Omitting it exits **0** and writes an object with **no device code**: 0 `__simt_vf__`
  instantiations, no kernel-type markers — the host half of the translation unit.
  Verified on identical sources: 35376 B / VF=0 without the flag, 14368 B / VF=8 with it.
  **Check codegen with `nm -C x.o | grep -c 'simt_'`, never with `$?`.** An exit-0 build
  with VF=0 is a failed build. Do not pass the flag to a command that links a `main()`
  (`cannot specify -o when generating multiple output files`). **The restriction is about the
  link phase, not the model** — it combines fine with Model A's `-cce-enable-puresimt` on a
  `-c` compile, and is mandatory there too.
  <!-- claim: cce-aicore-only-scope · also in: references/simt_build_and_compile.md · find with: grep -rn "claim: cce-aicore-only-scope" skills/simt-codegen · edit all sites together -->
- **`asc_atomic_add` *does* have 16-bit overloads — they are just in the dtype headers, not
  `device_atomic_functions.h`.** Include `asc_fp16.h` / `asc_bf16.h` and the native overload
  resolves; do **not** hand-roll a word-CAS for plain accumulation. The scalar overloads'
  *return value* is a non-atomic re-read, so they are safe to accumulate with and unsafe as a
  cursor. Coverage matrix, cursor caveat, and how to verify an atomic:
  [`simt_multi_dtype_guide.md` §Atomic add — dtype coverage](references/simt_multi_dtype_guide.md#atomic-dtypes).
- **A missing vendor header means the wrong front end, not a missing `-I`.**
  `--asc-aicore-lang` puts the ASC tree on the search path itself; the three `-I` paths
  above are belt-and-braces and adding a fourth fixes nothing. `-x cce` on a `.asc`
  fails with `'kernel_tpipe.h' file not found` no matter how many paths you add, and is
  also what produces `__hif8 is not supported on this target`. `-I.` **is** required
  when the kernel includes its own tiling header.
- `-xasc` must **not** be combined with `--asc-aicore-lang`.
- `-lm` is required for `std::exp`/`std::log`; it fails at link, so it looks like a codegen bug.
- A **non-puresimt** `__global__` entry (Model B/C) needs `KERNEL_TASK_TYPE_DEFAULT(...)`
  as its first statement, or `ld.lld` fails with *"auto derivate failed"*;
  `REGISTER_TILING_DEFAULT` alone is not enough. A **Model A** kernel must **omit** it —
  puresimt infers AIV routing, and the macro's header does not parse in that dialect, so
  adding it costs you the object. Measurements:
  [`simt_build_and_compile.md` §2.3](references/simt_build_and_compile.md#kernel-task-type).

## Workflow

All models follow: **Pass 0 (analysis)** → sequential code-gen passes → **Done**.
Each pass: generate code → compile → **inspect the artifact** → on failure: reference
check + retry (up to 3×).

> A pass is **not** green because the compiler exited 0. A device compile missing
> `--cce-aicore-only` exits 0 and emits an object with no device code at all. Gate every
> pass on the artifact — but **which** assertion depends on the artifact:
> on a relocatable `-c` object, `nm -C x.o | grep -c 'simt_'` > 0 **and**
> `grep -c Kernel_Type` >= 1. On the packaged binaries from a full msopgen build
> (`build_out/op_kernel/ascendc_kernels/binary/ascend950/{op}/*.o`), `Kernel_Type` is
> **0 by design** — post-link the AIV routing moves into the sibling `.json`
> (`core_type: "AIV"`). There, assert `simt_` > 0 plus `core_type == "AIV"` in that
> JSON. Applying the `-c` gate to `build_out` artifacts false-FAILs correct kernels.
> See `references/simt_build_and_compile.md` Quick Reference.

| Pass | Model A (pure SIMT) | Model B (SIMT VF) | Model C (SIMT+SIMD) |
|---|---|---|---|
| 0 | `analysis_pass` | `analysis_pass` | `analysis_pass` |
| 1 | `kernel_pass` — `__global__` kernel | `vf_pass` — `__simt_vf__` function | `simt_vf_pass` — `__simt_vf__` (→ UB) |
| 2 | `host_pass` — ACL + 4-arg launch | `entry_pass` — `__global__` + `asc_vf_call` | `simd_vf_pass` — `__simd_vf__` (Micro API) |
| 3 | `main_pass` — test + verify | `host_pass` — ACL + 3-arg launch | `entry_pass` — orchestrate VFs + DataCopy |
| 4 | — | `main_pass` — test + verify | `host_pass` — ACL + 3-arg launch |
| 5 | — | — | `main_pass` — test + verify |

## Sub-Agent Strategy

This skill must use a subagent to handle the complex multi-pass transformation:
- The subagent autonomously executes all passes sequentially
- Handles compilation errors with automatic retry (up to 3 attempts per pass). A pass
  counts as failed when the artifact lacks device code, even on exit 0 — see § Workflow
- Manages intermediate file state and error recovery
- Reports progress after each pass

1. Read `{op_name}_functional.py` and `op_desc.json`
2. Execute Pass 0 analysis to select SIMT model and configuration
3. Sequentially execute all code generation passes. After each pass, compile and handle errors.

**⚠️ CRITICAL: Always use `source build.sh`, NEVER `bash build.sh`.**
In docker+tmux environments, `bash build.sh` creates a new process group that receives SIGTTIN/SIGTTOU signals, causing cmake/make to stop silently. Using `source build.sh` executes in the current shell and avoids this issue.

**But `source` hides failures.** A `set -e` inside a sourced script does not halt
your shell, so a broken cmake/make can leave `$?` at 0 and the build looks green
when it is not. Never report a build as passing on `source build.sh` alone —
check the exit code and the artifact:

```bash
source build.sh; BUILD_RC=$?
ls build_out/*.run >/dev/null 2>&1 || BUILD_RC=1
[ $BUILD_RC -eq 0 ] || echo "BUILD FAILED (rc=$BUILD_RC)"
```

## Pass 0: Analysis (Model Selection + Configuration)

Read `{op_name}_functional.py` and `op_desc.json` to make the following decisions. These decisions drive all subsequent passes — no intermediate file is written.

### 0.1 SIMT Model Selection

Follow the Q1–Q6 decision flow below. Each question has explicit next-step pointers — follow them sequentially, do not skip questions.

<a id="ub-budget"></a>
**The UB budget** — stated once here, referenced by name everywhere else in this file:

| budget | value | applies to |
|---|---|---|
| **SIMT DataCache total** | 128 KB | all UB in the kernel; also the ceiling for VF-write → SIMD-read staging |
| **VF-readable window** | UB `[0, 8192)` | UB a VF reads through a **pointer passed in from the aicore half** |
| **static `__ubuf__` in a VF** | ~160 KB | arrays the VF declares itself — *not* bounded by the 8 KB window |

**Check these before picking a model, not while writing passes** — over the window, aicore→VF
ordering is unavailable and you are forced into chunked `asc_vf_call`s or a GM handoff.
**Allocate VF-readable buffers first:** the window is on the UB address, not the buffer or read size.
Both numbers, the two-device measurements, the differing failure modes, and the provenance are in
[`memory_optimization_guide.md`](references/memory_optimization_guide.md) §6, which is the source
of record; this table is the restatement that keeps the decision flow readable.
<!-- claim: vf-readable-ub-ceiling · also in: references/memory_optimization_guide.md · find with: grep -rn "claim: vf-readable-ub-ceiling" skills/simt-codegen · edit all sites together -->

**Q1. Does the operator have irregular/data-dependent memory access or control flow?**
(gather, scatter, indirect index, conditional mask, variable-length output, histogram binning, strided transpose)
- NO → **Vector or CV path** (not SIMT). Stop.
- YES → go to Q2

**Q2. Is the input access pattern contiguous?**
(reading elements in order — irregularity is only in output position or predicate, not in where you read from)
- YES, **and each input element has its own output slot** → **Vector path** — SIMD + mask is faster
  for contiguous scans.
  (NonZero SIMD was ~58× faster than SIMT stream compaction for contiguous input.)
  Stop.
- YES, **but many input elements accumulate into the same output slot** (histogram, bincount,
  scatter_add) → go to Q5.
  Contiguous input does not rescue these. SIMD has no same-slot accumulate, so a vectorized version
  must serialise the collisions, and that serialisation *is* the cost. Read-side contiguity is
  irrelevant when the contention is on the write side. See Q6 §Scatter-accumulate.
- NO → go to Q3

**Q3. Is there vectorizable compute fused with the irregular access?**
(elementwise like relu/add/mul/abs, or reduction like softmax/layernorm — applied after the irregular read)
- NO → go to Q5
- YES → **Model C** (SIMT+SIMD hybrid). UB data must fit [the UB budget](#ub-budget) — the DataCache row if the SIMD pipe reads what VF wrote, the VF-readable row if VF threads read UB themselves. Go to Q4.

**Q4. Is the fused compute purely elementwise?**
(no cross-element dependency — each output depends only on its own gathered input)
- YES → **Standard Model C**: `__simt_vf__` → `__simd_vf__` → DataCopy
  (GatherAndAdds: 1.64× faster than Model B. Ref: `references/operator_examples/gather_and_adds/`)
  Stop.
- NO (has reductions: max, sum, norm) → **Model C variant**: `__simt_vf__` → AscendC APIs in entry → DataCopy
  (MaskedSoftmax: ReduceMax/Exp/ReduceSum in `__aicore__` entry.
  Ref: `references/simt_operator_patterns.md` §Masked Reduction)
  `__simd_vf__` cannot compile reductions (`ReduceMax`, `ReduceSum`). These must go in the `__aicore__` entry function using AscendC high-level APIs.
  Stop.

**Q5. Does the operator need cross-thread cooperation?**
(threads must exchange data, synchronize, or accumulate into shared locations)
- NO → **Model B**, simple per-thread. Ensure ≥32 bytes/thread work.
  (Gather, CumSum, pure Scatter)
  Stop.
- YES → go to Q6

**Q6. What kind of cooperation?** (pick the first match)
- **Reduction** (the whole input must be ranked or accumulated to produce the output: topk, argmax, max, sum, sort)
  → Model B + `asc_shfl_down` butterfly + GM scratch (TopK: 5.5–8× vs serial)
  ⚠ **Sort → Model C, not Vector.** Keep the SIMT entry and call
  `Concat` → `Sort<T, true>` → `Extract` from the `__aicore__` half of the same kernel.
  A VF can call no `__aicore__` API; the aicore half of the same kernel can. Model A cannot —
  puresimt has no vector API. → `references/pass_details_model_c.md`
  ⚠ Use tensor tails for scratch, NOT OPP workspace (error 334)
- **Scatter-accumulate** (output indexed by input values: histogram, bincount, scatter_add)
  → **Model A** + per-warp `__ubuf__` atomics + grid-stride
  (Histogram: 1.29× vs built-in — see the note on that figure below)
  Low contention: per-thread atomic. High contention: warp-dedup (ballot+popc).
  Model B also works and is what you want if the op must ship as an msopgen VF kernel; the
  worked example in [`simt_advanced_patterns.md` §1.12](references/simt_advanced_patterns.md) is
  Model A, and so is the histogram we built and ran on device.
- **All-to-all exchange** (every element may move to any position: bitonic merge)
  → Model B + `__ubuf__` + `asc_shfl_xor` + `asc_syncthreads` (max 1024 elem/block)
- **Stream compaction** (variable-length output from non-contiguous input: sparse filtering, graph traversal)
  → **Model A** + `asc_ballot` + `__popc` + leader atomic
  (Model B also works, for the msopgen VF path. The compaction we built and ran on device is
  Model A, matching the example table in [`ARCHITECTURE.md`](ARCHITECTURE.md).)
  ⚠ Only for non-contiguous input — contiguous-input compaction (NonZero/Where) is faster in SIMD (see Q2)

> **On the Histogram 1.29× figure.** It is inherited from an SDK example, not something we have
> re-run. The installed CANN 9.1.0-beta.3 tree contains **zero `.asc` files**, so the cited source
> (`histogram.asc` lines 103-154) cannot be located, let alone rebuilt, on this box. Treat 1.29× as
> "SIMT was reported to beat the built-in at this shape," not as a reproducible benchmark or a
> target. The unqualified numbers elsewhere in Q4/Q6 (GatherAndAdds 1.64×, TopK 5.5–8×) *are* from
> our own runs.

**Cross-cutting rules** (apply after model selection):
- Never use OPP workspace for SIMT-writable memory (error 334) — use `__ubuf__` or tensor tails
- 2D transpose: `__ubuf__` tile + TILE_PAD=1 (4-byte) or TILE_PAD=2 (2-byte/half) + 1D→2D block flattening
- Batch dimension maps to blocks naturally — free up to 56 cores. For batch > 2×core_count, use grid-stride row loop (see `simt_operator_patterns.md` Warp Reduction section)
- Cross-thread data exchange → add warp functions (`asc_shfl_down` butterfly) + `asc_syncthreads`; include `simt_api/device_warp_functions.h` + `simt_api/device_sync_functions.h`
- Frequently-accessed input fits [the UB budget](#ub-budget) for the access pattern you need and access is random → add UB pre-staging (see `memory_optimization_guide.md` §6 for dual-allocator rules)
- UB staging (`__ubuf__` + `asc_syncthreads`) is **not** blanket-unavailable for narrow dtypes. A **native** `__ubuf__ half` tile is device-verified: `tile[32][32+PAD]` in a `__simt_vf__` passes at PAD=0 and PAD=2, 0/32768 mismatches, and the full Transpose2D kernel ran 0 mismatches over 786432 half elements. What *is* constrained is the **bitcast dodge** — carrying several dtypes through one `float` carrier tile — see `memory_optimization_guide.md` §9. If you hit 507035 on a UB path, suspect the causes in the error table below (unset tiling field → `dim3(0)`, oversized grid, `dim3` misuse) before blaming the dtype <!-- claim: half-ub-tile-availability · also in: references/memory_optimization_guide.md · find with: grep -rn "claim: half-ub-tile-availability" skills/simt-codegen · edit all sites together -->
- `ctz`/`ctpop`/bit-scan builtins are not instruction-selectable on ascend950 bisheng. Do not emit them
- VFs must be fully self-contained on the benchsite: benchsite AOT (9.1.0) silently drops VFs that call device helper functions (EZ1001, 0/20 on benchsite while local compile succeeds). Inline all helper logic
- For performance tuning during cake-evo rounds, read `references/simt_perf_tuning_rules.md` (bound classification, known ceilings, reusable levers)

### 0.2 Model Descriptions

**Model A — Pure SIMT** (`pure_simt`)
- **Structure**: `__global__` kernel function, 4-arg `<<<blocks, threads, ubuf, stream>>>` launch
- **Includes**: `acl/acl.h` + `simt_api/asc_simt.h` (NOT `kernel_operator.h`)
- **Has**: `__ubuf__` arrays, `asc_syncthreads()`, `asc_threadfence()`, `asc_atomic_*()`, `asc_shfl_*()`, `asc_ballot()`, `asc_reduce_*()`, `laneid()`, `lanemask_lt/eq()`, `__popc()`, `extern __ubuf__ char dynamicBuf[]`, `dim3(x,y,z)` 2D/3D grids, templates, struct args
- **Does NOT have**: `kernel_operator.h`, `asc_vf_call`, Micro API (LoadAlign, StoreAlign, DataCopy, etc.), `LocalTensor`, `Pipe`
- **Key advantage over Model B**: Templates work, struct args work, simpler code, CUDA-portable patterns
- **Use case**: Any operator that doesn't need Micro API — including histogram, transpose, Sobel edge detection, hash tables, and patterns with atomics/warp functions
- **Status**: Working on A950 (verified); official SDK release still pending. All warp/sync/atomic APIs verified in SDK examples (`histogram.asc`, `sobel_warp_shfl.asc`, `insert_hash_table.asc`, `matrix_transpose.asc`)
- **Example**: `simt_add/add.asc`, `histogram.asc`, `sobel_warp_shfl.asc`

**Model B — SIMT VF Bridge** (`simt_vf`)
- **Structure**: `__simt_vf__` function + `__global__ __vector__` entry with `asc_vf_call`, 3-arg `<<<>>>` launch (SDK uses `__vector__`; `__aicore__` may also work)
- **Restrictions**: VF must be free function (not class member); `__gm__` on all pointer args; `asc_vf_call` args are pointers + primitives only
- **Use case**: All operators; officially supported; warp/sync/atomic functions available
- **Example**: `simt_gather/gather.asc`
- **Ascend950PR ISA probes** (T1-sim verified, `Simt::` namespace variant):
  - `references/ascend950pr_isa_probes/simt.elementwise.binary.md` — full Model B boilerplate with `Simt::VF_CALL`
  - `references/ascend950pr_isa_probes/simt.reduce.warp-sum.md` — warp reduction + atomic combine pattern

**Model C — Hybrid SIMT+SIMD** (`hybrid_simd`)
- **Structure**: Extends Model B with two VF functions: `__simt_vf__` (irregular access) writes to `__ubuf__`, then `__simd_vf__` (vectorizable compute) processes UB data via Micro API, then `DataCopy` (MTE3) writes UB → GM
- **Restrictions**: Same as Model B + UB data must fit [the UB budget](#ub-budget); requires `SetFlag`/`WaitFlag` between V pipe and MTE3; `dynUBufSize > 0`
- **Use case**: Operators with BOTH irregular access AND regular vectorizable compute (e.g., gather + element-wise add)
- **Speedup**: ~22% for gather per SDK benchmarks (v1→v2)
- **Example**: `gather_v2.asc`, `references/operator_examples/gather_and_adds/`

### 0.3 Grid/Block Configuration

Unless overridden by `cake-evo`, use these defaults:

- `blocks_per_grid = 56` — matches AIV core count on Ascend 950 (`GetCoreNumAiv()` returns 56)
- `threads_per_block = 256` — 8 warps, proven default from SDK examples
- `dyn_ubuf_size = 0` — no dynamic UB allocation (Model A/B); calculated for Model C

**Dynamic grid sizing** — for operators where input size varies widely:
```
blocks = GetCoreNumAiv()
threads = min(ceil(total_elements / blocks), 2048)
if threads not multiple of 32: round up to next multiple of 32
```

**Batch dimension**: Batch elements map to blocks naturally. No special tiling needed — each row runs on a separate core (up to 56 cores on A950).

**Tunable range** (for future `cake-evo` SIMT integration):

| Variant | blocks_per_grid | threads_per_block | Use case |
|---|---|---|---|
| G-S1 | `GetCoreNumAiv()` | 128 | Small data, high register availability |
| G-S2 | `GetCoreNumAiv()` | 256 | Default (proven from SDK examples) |
| G-S3 | `GetCoreNumAiv()` | 512 | Medium data, good occupancy balance |
| G-S4 | `GetCoreNumAiv()` | 1024 | Large data, memory-bandwidth-bound ops |
| G-S5 | `ceil(N / 256)` | 256 | Data-proportional grid (very large N) |

**Constraint**: `threads_per_block` must be multiple of 32 (warp alignment).

### 0.4 Per-Thread Work Granularity

SIMT thread dispatch, bounds-checking, and address calculation have a fixed per-thread cost. Operators should aim for **≥32–128 bytes of work per thread** to keep overhead below ~5%. Below ~16 bytes/thread, more than 25% of cycles are wasted on dispatch/scalar/icache.

**Prefer loop-in-thread over more threads**:
```python
# GOOD: 256 threads × multi-iteration loop
for i in range(threadIdx.x, total, blockDim.x):
    output[i] = input[index[i]]

# BAD: N*S threads × 1 iteration each (high per-thread overhead)
output[idx] = input[index[idx]]
```

**Diagnostic**: ICache miss rate > 10% signals too little compute per thread. The fix is more work per thread, not larger code.

### 0.6 Performance Optimization Notes

Advisory hints for efficient code generation:

| Hint | When to use | Effect |
|---|---|---|

| `cache_hint=streaming/cached/store_streaming` | Known access pattern | `asc_ldcg/ldca/stcg` |

### 0.6.1 Float16 / Half Type Support

Half-precision (float16) has been validated end-to-end through the SIMT→UB→SIMD→DMA pipeline on Ascend 950PR.

| Concern | Rule |
|---|---|
| Bank-conflict padding | `TILE_PAD = 4 / sizeof(half) = 2` (not 1) |
| DataCopy alignment | Round up to 16 half elements (32 bytes): `(count + 15) & ~15u` |
| `__simt_vf__` half access | Include `simt_api/asc_fp16.h`; use `static_cast<half>(0)` for zero |
| `__simd_vf__` half compute | MicroAPI `Maxs`/`Adds`/`Muls` accept `half` operands directly |

**Validated operators**: GatherRelu (half SIMT GM→GM), GatherReluHybrid (half SIMT→UB→SIMD→DMA), Transpose2D (half UB tile with TILE_PAD=2)

### 0.6.2 Multi-Dtype Kernel Generation

**Default behavior**: Always generate templated kernels (`template <typename T>`) supporting float32, float16, and bfloat16 from a single source. Add `int32` for operators that move or select data without arithmetic on it (gather, scatter, transpose, concat). Skip templating only for fixed-output-type operators (index-only, histogram counts).

**Second dtype axis** — gather/scatter-family operators also vary the *index* type, `{int32_t, int64_t}`, independently of the data type: `template <typename T, typename IndexT>`. Instantiations are the cross-product, not the max — 4 data × 2 index = 8. Never hardcode `int32_t` for the index (int64 is PyTorch's default and would be silently rejected) and never use an unsigned index type where negative indices are legal. Pair with rule 10 below: the OpDef `.DataType()` lists must carry the same cross-product, or a registered combination has no kernel behind it.

**Key constraint**: Several warp/atomic intrinsics only accept 32-bit types. Widen half/bfloat16 to float before the intrinsic, narrow after:

| API category | 32-bit only? | half/bfloat16 workaround |
|---|---|---|
| `asc_shfl_down/xor/up` | Yes | `static_cast<float>()` → shuffle → `static_cast<T>()` |
| `asc_reduce_add/max/min` | Yes | Same widening pattern |
| `asc_atomic_add` | **No** — 16-bit is natively supported | Nothing to work around: include `asc_fp16.h`/`asc_bf16.h` and the native overload resolves. Coverage varies by header and memspace — [dtype coverage matrix](references/simt_multi_dtype_guide.md#atomic-dtypes). Scalar 16-bit return is a non-atomic re-read: accumulate yes, cursor no |
| `asc_ballot/__popc/laneid` | No | Works with any data type |

**Sizeof-dependent constants** — never hardcode; use `sizeof(T)`:
- UB 2D tile padding: `4 / sizeof(T)` elements
- DataCopy alignment: `32 / sizeof(T)` elements

**Full patterns, widening helpers, and instantiation guide**: [`references/simt_multi_dtype_guide.md`](references/simt_multi_dtype_guide.md)

### 0.7 Restrictions

#### Workspace Buffer Restriction (All SIMT Models)

**CRITICAL**: The OPP workspace buffer (4th `GM_ADDR` parameter in `__aicore__` kernels, allocated via `GetWorkspaceSizes()`) is **NOT SIMT-writable**. Any SIMT write to workspace causes `error code = 334: BIU→VEC data error`.

Generated SIMT operators must:
- Set workspace size = 0 (`workspace[0] = 0` in TilingFunc)
- Use tensor tails or dedicated scratch tensors for any SIMT-writable memory
- Never pass the workspace pointer to a `__simt_vf__` function for writing

#### Model A Restrictions

- Kernel is a `__global__` free function (4-arg `<<<blocks, threads, ubuf, stream>>>` launch)
- Plain `T*` pointer args. **Do NOT write `__gm__` on a Model A kernel param** — under
  `-cce-enable-puresimt` the macro expands to `__attribute__((device))`, which is not a valid
  parameter qualifier, and the build dies with `error: __constant__, __device__, and __managed__
  are not allowed on non-static local variables`. `__gm__` is *required* on Model B/C VF params,
  so it is model-specific, not optional-everywhere — carrying it across models is a build break,
  not a harmless habit.
- Includes: `acl/acl.h` + `simt_api/asc_simt.h` (NOT `kernel_operator.h`)
- HAS full SIMT API access: `__ubuf__`, `asc_syncthreads()`, `asc_atomic_*()`, `asc_shfl_*()`, `asc_ballot()`, `asc_reduce_*()`, `laneid()`, `lanemask_lt/eq()`, `__popc()`, `gridDim.x`, `dim3(x,y,z)` 2D/3D grids, templates, struct pointer args
- Does NOT have: `asc_vf_call`, `kernel_operator.h`, Micro API (LoadAlign, StoreAlign, DataCopy), `LocalTensor`, `Pipe`

#### Model B/C Restrictions

- VF function must NOT be a class member (free function or static method only)
- `asc_vf_call` args: only raw pointers (`__gm__ T*` or `__ubuf__ T*`) and primitives (no structs, no arrays)
- `__gm__` qualifier required on all VF pointer params (except `__ubuf__` for Model B pre-staged inputs or Model C UB targets)
- Thread count in `dim3` must be ≤ 2048 and multiple of 32

#### Error Handling

If the operator cannot be expressed in SIMT:
1. Check if it requires dynamic parallelism (SIMT within SIMT) — not supported
2. Check if it requires shared memory beyond [the UB budget](#ub-budget) — use Model C or fail
3. Check if it requires inter-block communication — not supported, report as non-SIMT-able

Emit clear error message and suggest Vector path fallback.

## ⚠️ CRITICAL Rules

These are the most common codegen mistakes. Code examples are in the pass details files; the error correction table above has the fix for each.

1. **VF must be a free function** (Model B/C) — class member VFs fail `asc_vf_call`. Extract to top-level.
2. **Launch arity must match model** — Model B/C: 3-arg `<<<blocks, ubuf, stream>>>`. Model A: 4-arg `<<<blocks, threads, ubuf, stream>>>`. Mixing them silently misinterprets parameters.
3. **Warp functions: correct context only** — Model B: warp/sync/atomic calls go inside `__simt_vf__`, NOT in the `__global__ __vector__` entry. Model A: warp calls go directly in `__global__` kernel (verified in SDK).
4. **Pipe sync before UB reads** — After `asc_copy_gm2ub_align` (MTE2), always `asc_sync_notify`/`asc_sync_wait(PIPE_MTE2, PIPE_V)` before `asc_vf_call`. Missing sync → stale/garbage UB data.
5. **`__simd_vf__` cannot do reductions** (Model C) — Reductions (ReduceMax, ReduceSum) go in the `__aicore__` entry function, not `__simd_vf__`. See `references/pass_details_model_c.md` for the decision heuristic and code pattern.
6. **Fill the whole tiling contract** (msopgen) — every field the kernel reads from `<Op>CustomTilingData` MUST be set in `TilingFunc`, derived from shapes/attrs/dtypes, plus `context->SetBlockDim(numBlocks)`. An unset field arrives on-device as **0** → `dim3(0)` invalid grid / `innerSize=0` div-by-zero / wrong dtype branch (**error 507035**). Never leave a field at a hardcoded constant with a "compile-only"/"populated at runtime" comment. See `references/msopgen_adaptation.md` Step 2b. Check this by hand before finishing — no automated gate covers it yet.
7. **`asc_vf_call` is per-core synchronous only** — With `SetBlockDim > 1`, two `asc_vf_call`s in one `__aicore__` entry have **no cross-core ordering guarantee**. A cell written by VF-1 on core A can be overwritten by VF-2 on core B that hasn't finished VF-1 yet. `SyncAll<true>()` between VF calls does NOT fix this — verified on A5 (Ascend950PR, CANN 9.0.0-beta.2): VF sub-tasks are async relative to the SIMD entry. **This is a durable hardware finding — do not re-test.** Safe alternatives: (1) two separate kernel launches with a phase attr — stream ordering serializes them; (2) `SetBlockDim(1)` for small data only. See `references/simt_debug_patterns.md`. When the multi-launch perf cost matters, `references/builtin_parity_optimizations.md` §2 shows how to collapse to a single in-place kernel — only after correctness is confirmed.
8. **Grid-stride + numBlocks cap for data-driven element counts** — When thread count comes from a runtime shape, the grid can grow unbounded. At ~65536 blocks the vector core faults (507035). Host: `numBlocks = min(ceil(N / threadsPerBlock), 32768)`. Kernel: every VF must grid-stride: `for (i = tid; i < N; i += gridDim.x * blockDim.x) { ... }`. An inconsistency (one VF strides, another doesn't) is itself a bug. The `if (tid >= N) return;` one-element pattern is valid **only** for fixed-small-N.
9. **No silent wrong-answer fallbacks** — If the OpDef registers a mode/dtype combination, the kernel MUST implement it correctly. An `else { output[i] = update_val; }` fallback for an unimplemented path is **banned** — it compiles, runs, and produces output that might even pass some tolerance checks. Either implement the path (CAS loops for multiply, word-CAS for half/bf16 atomics — see `references/simt_multi_dtype_guide.md`) or remove the OpDef registration. A compile error is strictly preferable to a silent wrong answer.
10. **OpDef `.DataType()` lists are positional tuples** — Index *i* across all Input/Output tensors defines one valid dtype combination. When ≥2 inputs have independently varying dtype axes (data=float family, indices=int family; input=float, mask=bool), the entries must be the **full cross-product** (∏ axis sizes), not the diagonal. Example: 5 data dtypes × 2 index dtypes = 10 aligned entries, not `max(5,2)=5`. All Input/Output `.DataType()` and `.Format()` arrays must be equal length. See `references/msopgen_adaptation.md` Step 2a.
11. **`dim3(...)` in `asc_vf_call` is threads-per-block, NOT grid size** — `asc_vf_call<VF>(dim3(N), ...)` launches N threads **within one block** (must be ≤ 2048; default 256). The grid (number of blocks) is set separately on the host via `SetBlockDim(numBlocks)`. Passing `dim3(totalBlocks)` or `dim3(numBlocks)` as the thread count makes threads = blocks × blocks (nonsensical) and crashes (507035) on any non-trivial input. This was the cause of transpose's crash on every real-scale case.
    <!-- claim: model-b-grid-is-1d · also in: references/simt_operator_patterns.md · find with: grep -rn "claim: model-b-grid-is-1d" skills/simt-codegen · edit all sites together -->
12. **Per-launch array metadata → immutable tiling pointer, never `__gm__` globals** — When the VF needs per-launch arrays (shapes, strides, perm), pass the tiling struct pointer (`__gm__ const <Op>CustomTilingData*`) directly as a VF argument. **Never** copy tiling arrays into mutable `__gm__` globals in the entry and read them from the VF — the entry write and VF read have no cross-core ordering (rule 7), causing stale/zero metadata on cold launch. This was the dominant failure for both gather (flaky wrong values, round_2 ~2–4/10) and transpose (all-zero output). See `references/pass_details_model_b.md` §1.2.
13. **Kernel owns every output element (strict wrapper rule)** — The wrapper hands an uninitialized (`empty`) buffer. The kernel MUST write every output position — including positions the main computation doesn't actively touch (un-scattered base elements, reduction identity, copy of input). **Do NOT assume the output is pre-initialized.** Do NOT put `data.clone()`, `data.copy()`, or `torch.zeros_like()` in the wrapper — the wrapper must be a thin pass-through. Strategies to achieve full output coverage without triggering the cross-core VF hazard (rule 7): **(a)** Fused per-position select (preferred when the output domain is enumerable): each thread writes every output element in one pass — `out[i] = is_scattered(i) ? update : data[i]`. Works for `masked_fill`, `where`, scatter with enumerable output. **(b)** Two-launch kernel (for scatter with non-enumerable targets or when base-copy + sparse-write must be separate): Launch 1 = grid-stride memcpy kernel (`output[i] = data[i]`), Launch 2 = scatter kernel. Stream ordering guarantees Launch 1 completes before Launch 2. Use a `phase` tiling attr to dispatch from one OpDef. See `references/simt_operator_patterns.md` §Deterministic Cross-Core Ordering. **(c)** Single VF with grid-stride copy+compute — one VF does `output[i] = data[i]` for all `i`, then a second grid-stride loop applies scatter writes. Safe because it's a single VF (no cross-core ordering issue within one VF). Only correct when `SetBlockDim(1)` or when copy and scatter ranges don't overlap across cores. (round_2 scatter scored 0/20 because the kernel wrote only the scattered positions and left the rest garbage; round_3 used wrapper `data.clone()` as a workaround, now banned.)
14. **Only submit to the real benchsite AFTER a full local 20/20** — Do **not** hand-craft an aclnn bundle or run `cake_submit.py` until the complete contract-spanning local suite passes **20/20** on-device against the independent CPU fp64 golden + index-check (all dtypes × dim × largest × k-range × ranks × inf/nan/zero). A remote submission is expensive and slow; a local partial pass (e.g. 15/20, or happy-path-only) predicts nothing about the real score (we saw 52.7 local vs 1/20 real). Local 20/20 is the **gate**, not the goal — the goal remains real-benchsite 20/20 — but never spend a remote submit to *discover* a bug the local suite would have caught. Fix locally first, re-run the full suite, and only then submit.

## Editing these docs: claim cross-references

**First rule: give each fact one home and link to it.** A fact written out in N places drifts
in N places. The atomic dtype matrix was stated in five files and three of them disagreed; the
VF-readable UB ceiling was restated at four points in this file alone. Both now have a single
canonical section ([dtype coverage](references/simt_multi_dtype_guide.md#atomic-dtypes), [the UB
budget](#ub-budget)) and everything else links by name. Links cannot go stale, so they need no
bookkeeping — prefer an anchor link over a copy even when the copy would be one line shorter.

**Markers are for the residue.** A few facts genuinely have to be written out twice, because a
reader who opens only one of the two files still needs the answer — the UB budget belongs in the
decision flow *and* in the memory guide, and the atomics summary belongs in `ARCHITECTURE.md`
*and* in the dtype guide. Those sites carry a marker so an editor changing one finds the other:

```html
<!-- claim: some-fact-slug · also in: references/other_file.md · find with: grep -rn "claim: some-fact-slug" skills/simt-codegen · edit all sites together -->
```

Three constraints on markers, all learned by breaking them:

- **Tag every site or none.** A one-directional pointer is not traceability. If a slug ends up
  with a single site, either its siblings were never tagged, or the claim got consolidated and
  the marker should be deleted.
- **Never put line numbers in `also in:`.** They rot on the next edit — we shipped markers aimed
  at `SKILL.md:349` after the row had moved to 356. Name the file; the grep locates it.
- **Do not mark a site that only links.** Marking a link implies there is something to keep in
  sync when there isn't, and it inflates the count so real duplication hides in the noise.

`scripts/check_claim_xrefs.py` enforces all three in CI and has a `--self-test`. It ignores
markers inside fenced code blocks, so the example above does not count as a site.
