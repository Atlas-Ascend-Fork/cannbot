# `GET_TILING_DATA` Pattern Guide

## Overview

`GET_TILING_DATA` is **not defined in CANN SDK headers**. It is generated at build time by msopgen's build system. For standalone compilation or quick syntax checks, you need to provide a fallback definition in your tiling header.

## Pattern: Explicit Type Per Operator

This is the recommended and proven approach. Each operator's tiling header defines its own struct and a fallback macro using the explicit type.

### Example: Gather Operator

**File**: `gather_custom_tiling.h`

```cpp
#ifndef GATHER_CUSTOM_TILING_H
#define GATHER_CUSTOM_TILING_H

#include <cstdint>

// Define the tiling data structure for this operator
struct GatherCustomTilingData {
    uint32_t totalElements;
    uint32_t threadsPerBlock;
    uint32_t dtypeCode;           // 0=float, 1=half, 2=bfloat16
    uint32_t inputShape[8];
    uint32_t outputShape[8];
    uint32_t inputStrides[8];
    uint32_t axis;
    uint32_t ndim;
};

// Fallback for standalone .asc compilation
// msopgen's build system will #undef and override this with its own version
#ifndef GET_TILING_DATA
#define GET_TILING_DATA(name, tiling_ptr) \
    const __gm__ GatherCustomTilingData& name = \
        *reinterpret_cast<__gm__ const GatherCustomTilingData*>(tiling_ptr)
#endif

#endif  // GATHER_CUSTOM_TILING_H
```

### Key Points

1. **Use the explicit tiling struct type** (e.g., `GatherCustomTilingData`) — not a generic type
2. **Use `const __gm__` reference** — the tiling data is immutable and lives in global memory
3. **Guard with `#ifndef`** — msopgen will `#undef` and redefine this macro with its own implementation
4. **Self-contained** — requires no external dependencies or build system support

### Usage in Kernel

This example is a non-puresimt AscendC entry (`__global__ __aicore__`), which is why
it carries `KERNEL_TASK_TYPE_DEFAULT`. Which dialects need that macro — and which
must omit it — is in
[simt_build_and_compile.md §2.3](simt_build_and_compile.md#kernel-task-type).

```cpp
#include "gather_custom_tiling.h"

extern "C" __global__ __aicore__ void gather_custom(
    GM_ADDR input, GM_ADDR indices, GM_ADDR output,
    GM_ADDR workspace, GM_ADDR tiling)
{
    KERNEL_TASK_TYPE_DEFAULT(KERNEL_TYPE_AIV_ONLY);
    REGISTER_TILING_DEFAULT(GatherCustomTilingData);
    GET_TILING_DATA(td, tiling);

    // Use tiling data
    uint32_t totalElements = td.totalElements;
    uint32_t axis = td.axis;
    // ...
}
```

## Why This Pattern?

### Why not use a generic type?

`REGISTER_TILING_DEFAULT` does **not** create a typedef. It only creates linker section metadata:

```cpp
// From kernel_utils_macros.h
#define REGISTER_TILING_DEFAULT(tiling_struct) \
    ENABLE_FEATURE_FOR_TILING(default, tiling_struct)

// Expands to:
// static const uint64_t __ascendc_tiling_struct_##counter
//     __attribute__((used, section(".ascendc_tiling."#val))) = sizeof(val)
```

There is no `__TilingDataType__` typedef available.

### Why not use `auto`?

Using `auto` with `__gm__` address space qualifiers is untested and unsupported:

```cpp
// ❌ UNTESTED — no evidence this works with __gm__ qualifier
#define GET_TILING_DATA(name, tiling_ptr) \
    const __gm__ auto& name = \
        *reinterpret_cast<__gm__ const auto*>(tiling_ptr)
```

The interaction between `auto` type deduction and `__gm__` address space qualifiers has zero evidence of working in SIMT code.

### Why explicit type is best

- ✅ **Proven in production** — already deployed and verified
- ✅ **Self-contained** — no build system dependencies
- ✅ **Clear and greppable** — obvious what type is being used
- ✅ **Stable across CANN versions** — doesn't rely on internal implementation details
- ✅ **Works for standalone compilation** — enables quick syntax checks

## msopgen's Generated Version

When building through msopgen, the build system generates `{op}_tiling_data.h` which includes:

```cpp
// Generated by msopgen build system
#undef GET_TILING_DATA
#define GET_TILING_DATA(td, ta) \
    GatherCustomTilingData td; \
    InitGatherCustomTilingData(ta, &td)
```

The generated version:
- Declares a **non-const local variable** (not a reference)
- Calls an `Init*` function to copy from `__gm__` to local storage
- Has both host and device overloads (selected by `-D__NPU_TILING__`)

The fallback pattern's reference-based approach is **incompatible** with the generated version at the variable declaration level, but that's intentional — msopgen's `#undef` ensures its version takes precedence when building through the project.

## Template for New Operators

When creating a tiling header for a new operator:

```cpp
#ifndef {OP_NAME}_CUSTOM_TILING_H
#define {OP_NAME}_CUSTOM_TILING_H

#include <cstdint>

struct {OpName}CustomTilingData {
    uint32_t totalElements;
    uint32_t threadsPerBlock;
    uint32_t dtypeCode;
    // ... operator-specific fields
};

#ifndef GET_TILING_DATA
#define GET_TILING_DATA(name, tiling_ptr) \
    const __gm__ {OpName}CustomTilingData& name = \
        *reinterpret_cast<__gm__ const {OpName}CustomTilingData*>(tiling_ptr)
#endif

#endif  // {OP_NAME}_CUSTOM_TILING_H
```

Replace `{OP_NAME}` and `{OpName}` with your operator name in the appropriate case.

## Compilation

With this pattern, standalone syntax checks work without any build system:

```bash
bisheng --asc-aicore-lang --npu-arch=dav-3510 --cce-aicore-only \
  -std=c++17 -O2 -D__NPU_TILING__ \
  -I"$A/include" -I"$A/asc/include" -I"$A/asc/impl" -I. \
  -c my_op_custom.cpp -o my_op.o

nm -C my_op.o | grep -c 'simt_'   # must be > 0
```

`-I.` is required so the compiler finds your tiling header. `--cce-aicore-only` is
required too: without it the compile still exits 0 but emits a host-only object with
no device code, so the fallback macro would appear to work while nothing was checked.
See [simt_build_and_compile.md](simt_build_and_compile.md#quick-reference).
